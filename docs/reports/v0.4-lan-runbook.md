# v0.4 LAN acceptance runbook

Status: run once on a single machine with real components (2026-10-30, below); the three-computer run on the LAN is still the author's. The automated Chromium scenario uses three browser contexts on one machine and cannot establish SMB, LAN certificate trust or reverse-proxy behavior on the deployment network. Record the date, versions, job IDs, outcomes and deviations below before accepting a release.

## Preparation

1. On a **Linux** server, install Archiwista with the Kartograf producer and its matching pinned version (see `pyproject.toml` and `archiwista doctor`). Mount a test SMB share as the server account, with a writable Kartograf store and a separate project directory. The store needs hard links on the share (each slot links to its version, SPEC 4.4): the Linux CIFS client creates them (the v0.1 and v0.2 measurements kept the store on an SMB 3 share), while the macOS SMB client answered `os.link` with `ENOTSUP` on an SMB 3.1.1 mount even though the server advertised Unix support, so a macOS server can keep projects on the share but not the store. Check that the server account can create a file on the share and that the three clients can reach the server by its DNS name. Keep production data and the test store separate. Back up state before an upgrade: `archiwista state export --output /secure/archiwista-before-v04.json` (mode `0600`; contains password hashes).
2. Install a TLS certificate and key readable only by the server account. Trust its issuing CA on **each** of the three computers and verify the certificate name matches the HTTPS origin in each browser. Either use TLS in Archiwista (`tls_cert` and `tls_key`) or terminate it at a trusted reverse proxy as described in `docs/USAGE.md`, “Team server”; never expose a plain HTTP listener to the LAN. Record whether the CA is public or internal (the latter is the documented ASVS 12.2.2 deviation).
3. Stop the server and configure the store and project directory in `config.toml`, plus `[team]`, for example:

   ```toml
   [team]
   enabled = true
   origin = "https://archiwista.firma.local:8443"
   tls_cert = "/etc/archiwista/tls/fullchain.pem"
   tls_key = "/etc/archiwista/tls/privkey.pem"
   ```

   For proxy termination, omit both TLS file keys, set `trusted_proxies` and bind the backend to `127.0.0.1`; configure proxy forwarding and header replacement per `docs/USAGE.md`. Do not enable `proxy_user_header` unless the proxy authenticates and overwrites the header. Use the same host and port in `origin` that the browsers open.
4. At the server terminal, create accounts before starting: `archiwista users add anna --name "Anna" --role admin --role store_writer`, `archiwista users add marek --name "Marek" --role store_writer`, `archiwista users add kasia --name "Kasia"`. Set each password with `archiwista users password ID` (repeat for each ID; enter privately). Set up group `hydro` with Kasia but not Marek in “Grupy” after sign-in. Check `archiwista users list` and `archiwista doctor`; never put passwords in this report.
5. Start `archiwista serve --host 0.0.0.0 --port 8443` for TLS in Archiwista, or `archiwista serve --host 127.0.0.1 --port 8090` behind a local trusted proxy. Open the configured HTTPS origin from all three computers. Confirm no certificate warning, sign in Anna, Marek and Kasia separately, and confirm each person's name in the account menu. Do not bypass certificate validation.

## Three-person scenario

1. In Anna's and Marek's browsers select the same Kartograf store and overlapping stations/units that are not yet present. In “U źródła”, make two plans with at least one common file and at least one distinct file for each person. Record the unit IDs, the store version and both plan/job IDs. Start Marek's planned download first while it is still transferring; start Anna's overlapping plan before it completes. If the first finishes too fast, use a larger test unit or a throttled test share; do not infer concurrency from sequential jobs.
2. While both jobs run, Anna's “Zadania” must identify the claimed overlap as “pobiera Marek”; Kasia's “Zadania” must show both jobs with their owners, but she cannot start a store download: the action is disabled with a reason. If she tries the HTTP download route, it must answer `403` and create no job. Record a screenshot or the observed messages without including credentials.
3. Kasia creates a project in a free project directory and shares it with group `hydro`; Anna can see it as administrator, and Marek cannot see it. In Anna's “Dziennik”, check the three sign-ins, job starts and Kasia's refused action with actor, time, client and outcome. Export the log through the view or `archiwista log export --output /secure/archiwista-v04-log.jsonl` (keep it private).
4. While Marek already has two network jobs active, submit his third network job; it must wait (his limit, `network_jobs_per_person`). The server also runs at most two network jobs at once (ADR-047 decision 4), so Anna's independent network job submitted now waits too; the rule to check is the fair start: when one of Marek's jobs ends, Anna's job takes the free place before Marek's third, because she has fewer running network jobs. Check the actual running/queued states rather than relying on list order. Once both overlapping jobs finish, use `archiwista jobs show JOB --json` for each job: for each common file, one job's `files` must hold it as `new` and the other job's `result.taken` must name it with the job and actor that took it; the store contains a single version of that file. Verify the non-overlapping files were downloaded as planned. This is the live proof of no duplicate fetch; a single stored version alone does not prove that it was only fetched once.
5. Sign Marek out; verify his browser returns to “Logowanie” on its next request and Anna's and Kasia's sessions stay active. Restore test accounts, projects and test-store files only after recording the results; keep the exported log and database backup under restricted access, then remove them according to the team's retention policy. Stop the test server and revert the test `[team]` configuration if this is not the permanent deployment.

## Result

### Single-machine run (2026-10-30)

Real components throughout on one machine: a real Kartograf store, a real TLS listener, three real accounts over HTTPS, real GUGiK downloads (723 MB). Server commit and Kartograf version were not recorded in the run's report.

| Step | Result |
|---|---|
| Preparation 1, state backup | `state export` writes mode `0600` and warns that it holds password hashes |
| Preparation 2, TLS | internal CA; `curl --cacert` verifies, HTTP 200, no bypass; internal CA = the ASVS 12.2.2 deviation |
| Preparation 3, configuration | store, project directory and `[team]` validate; `doctor` 0 errors, 0 warnings |
| Preparation 4 and 5, accounts and sign-in | Anna admin + store_writer, Marek store_writer, Kasia no role, group `hydro` = Kasia; all three sign in over HTTPS with their roles and groups; Kasia `store_write: false` |
| Scenario 1, overlapping plans | 12 positions each, 4 common and 8 distinct per person; Marek's download at unit 1/12 when Anna's started, both running together for about 220 s |
| Scenario 2, Kasia refused | `403 permission_denied`, no job, in Polish and English |
| Scenario 3, project and sharing | project created in the project directory on the SMB share, shared with `hydro`: Anna sees it, Marek does not |
| Scenario 3, „Dziennik” and export | sign-ins, job starts, Kasia's `permission.denied`, an audited `request.refused`; Kasia gets `403` on the log; export of 48 JSONL entries, mode `0600` |
| Scenario 4, limit per person | Marek's third network job queued while two ran |
| Scenario 4, no duplicate fetch | Anna's `result.taken` holds exactly the 4 common units, each naming Marek's job `511705dfd0399732` and actor `marek`; Marek fetched all 4 as new, Anna none; the two sets of new units are disjoint, 20 unique units for 12 + 8 planned; each common unit has one version in the store, its standard path a link to the same inode |
| Scenario 5, sign-out | `204`; Marek `401` on his next request; Anna and Kasia stay `200` |

Deviations found and their remediation (fixed in the runbook and messages on 2026-10-30):

- Step 4 asked for Anna's job to start while Marek ran two network jobs; the server's limit of two network jobs (`MAX_NETWORK_JOBS`, ADR-047 decision 4) makes it wait. The step now checks the fair start instead.
- The store cannot be on an SMB share mounted by macOS (`os.link` → `ENOTSUP`); preparation 1 now asks for a Linux server. Projects on the share work from macOS.
- The English refusal text of `store_write` quoted the Polish permission name; fixed in `messages/permission.py`.
- Step 3 named the log field "source"; the field is `client`.

Not covered by this run: three separate computers, CA trust in three browsers on the LAN, a reverse proxy, the store on an SMB share. Acceptance decision: the author's, after the three-computer run.
