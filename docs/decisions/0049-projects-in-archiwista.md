# ADR-049: Projects are Archiwista's own: the file `archiwista-project/1`, groups of pins, and the jobs over them

**Date:** 2026-10-31
**Status:** accepted (the author's decision of 2026-10-31: option B and the recommended answer of D1 to D7 of the Nogat plan `docs/plans/2026-10-31-archiwista-projects.md`, recorded as ECO-054; built on `feature/archiwista-projects` in the phases P2 to P6 of [`docs/plans/2026-10-31-archiwista-projects.md`](../plans/2026-10-31-archiwista-projects.md)); supersedes ADR-039, ADR-040, ADR-032 decision 14 and the IMGWTools manifest of ADR-023; partly supersedes ADR-042 (decisions 3 and 4)

**Context:** Until now a project of Archiwista was a directory holding a producer's manifest, `kartograf-project.json` (`kartograf-project/1`), `imgw-project.json` (`imgw-project/1`) or both (ADR-032 decision 14, A-ADR-023). The tasks of a manifest (a producer's data command with its options) and their pins were the producer's, written only through the producer's API: `ProjectActionAdapter` created a project and added or removed a task (ADR-039), and the jobs `project_download`, `project_repin`, `project_check` and `project_verify` ran the producer's `download_project`, `check_project` and `verify_project` (ADR-040). Access, own data and snapshots were Archiwista's (A-ADR-027, A-ADR-029), and the "Zestaw" (SPEC 8.4, v1.1) was a notion of its own. In the producers' model a pin exists only inside a task and only after a full run of its command: data the store already holds is pinned only by adding a command whose run finds it there, no version can be pinned as it is, and a project has no area, no activity and no export.

On 2026-10-31 the author decided that projects belong to Archiwista alone (ECO-054; option B of the Nogat plan). Kartograf and IMGWTools remove their projects (neither released them, so no user breaks, ECO-020) and gain one read-only function each, the command of a stored version from its metadata as a `CommandCall`: Kartograf's `command_for_file(sidecar)` (KB-6) and IMGWTools' `command_for_version(version, *, root=None)` for a stored archive or series version (a path relative to the store). Both refuse with their error class, `code` `unsupported` and `details["reason"]` `command_not_rebuildable` where the metadata does not rebuild the call (Kartograf: land cover and collections chosen by a box, CZ collections by a box, the derived `soil hsg`). `run_command`, `check_command`, `format_command`, `parse_command`, the store read APIs and the sidecars (IMGWTools' `content_sha256` too) stay. The author also settled the plan's open decisions, each with its recommended answer: the project is a file in its directory, with its access in the state database (D1); one release of Archiwista holds v0.3, v0.4 and the projects (D2); Archiwista leaves the first release set (D3); no producer manifest is migrated (D4); a version whose command cannot be rebuilt is pinnable, with "check" and "restore" disabled with the reason (D5); the exports are `pliki.txt` and `ATRYBUCJE.txt` now and the QGIS export in v1.1 (D6); a project's activity is the action log filtered by the project (D7). Open for this ADR: the file's shape and how it is written on a share, discovery and the index, how a version the store holds is pinned and how data downloaded through the plan window is, what replaces `ProjectActionAdapter` in the source interface, the jobs, the exports and the activity.

**Options:**
- Who keeps projects (the Nogat plan): A) the producers' manifests under one view of Archiwista. Rejected: the split stays under the surface, and a version is pinned only through a producer's task. B) Archiwista alone. C) A shared project library imported by every tool. Rejected: a dependency of every tool for a notion only Archiwista presents. D) Release the producers' projects and move them later. Rejected: a released interface broken by the next release.
- Where a project is kept (D1): a) `archiwista-project.json` in the project's directory, its access in the state database; b) everything in the state database. Rejected: it is lost with the state database, does not travel with the directory or the share, and no other tool can read it.
- How the file is written on a share: E) a lock directory made with `mkdir` beside the file and an atomic replace of the whole file, as Kartograf and IMGWTools wrote their manifests on SMB without byte-range locks (SPEC 4.6); F) SQLite in the project's directory. Rejected: no SQLite file on a share (A-ADR-002); G) byte-range locks. Rejected: unreliable on SMB (SPEC 4.6).
- Members a reader does not know: H) a reader ignores them and a writer keeps them, so an older Archiwista of a team does not lose what a newer one added within `/1`; I) refuse them. Rejected: every additive member would need `/2`, and two versions of Archiwista on one share could not share a project.
- How data downloaded in the plan window is pinned: J) the `download` job pins at its end when its request names a project and a group (`pin`): its `files[]` and the positions of its plan it did not transfer; K) the browser pins after the job ended. Rejected: a closed tab loses the pin; L) a project job of its own that runs the calls without the plan window's plan. Rejected: the plan the person saw and the claims of ADR-047 would not apply.
- What replaces `ProjectActionAdapter`: M) one optional capability, `VersionCommandAdapter.command_for_version`, beside `ActionAdapter.check` and `run`; N) a project capability in each adapter. Rejected: a project is no producer's notion any more.

**Decision:** B, D1 a, E, H, J and M, with D4 a (no migration), D5 a, D6 a and D7 a.

1. **The file.** A project is a directory holding `archiwista-project.json`: UTF-8 JSON, `schema` `archiwista-project/1`, written only by Archiwista on a person's command (an open format, readable without Archiwista, like the snapshots of A-ADR-027). For example:

   ```json
   {
     "schema": "archiwista-project/1",
     "name": "Raba",
     "description": "Zlewnia Raby do Dobczyc",
     "created_at": "2026-10-31T12:04:11Z",
     "created_by": "kasia",
     "area": {"path": "obszary/5f2b9c0e7d41a3b6.geojson", "sha256": "<64 hex>"},
     "stores": [{"producer": "kartograf", "root": "../../dane/kartograf"}],
     "groups": [
       {
         "name": "NMT 2023",
         "origin": {
           "kind": "plan",
           "producer": "kartograf",
           "calls": [{"command": "elevation download", "options": {"product": "nmt", "sheet": "N-34-130-D-d-2-4", "year": 2023}}]
         },
         "pins": [
           {
             "producer": "kartograf",
             "version": "nmt/pl_1992_1m_evrf2007/versions/N-34/130/D/d/2/4/2023-05-02_80011_fdd30535/N-34-130-D-d-2-4.asc",
             "sha256": "<64 hex>",
             "size_bytes": 37812345,
             "unit": "N-34-130-D-d-2-4",
             "label": "2023-05-02_80011",
             "pinned_at": "2026-10-31T12:20:03Z",
             "pinned_by": "kasia"
           }
         ]
       },
       {
         "name": "Archiwa hydro",
         "origin": {"kind": "local", "selections": [{"from": "catalog", "query": {"store": "zespol", "product": "hydro", "years": "1991-2020"}}]},
         "pins": []
       }
     ]
   }
   ```

   - `name` (1 to 200 characters after NFC and trimming, no control character) and `description` (at most 2,000 characters; `""` when left out); `created_at` (UTC, `YYYY-MM-DDTHH:MM:SSZ`, as every time of the file) and `created_by` (the account's id; `local` for the local owner; an agent's account for an agent).
   - `area`: `null` (or left out), or the project's geometry file (decision 4): `path` relative to the project's directory, `/`-separated, below `obszary/`, and `sha256` of its bytes.
   - `stores`: at most one per producer, `{"producer", "root"}`; `root` is the producer's directory of a configured store as written when it was added: relative to the project's directory when the store has path aliases (SPEC 4.6 point 7) and a relative path exists (the same drive), else absolute; never the producer's default root (A-ADR-033).
   - `groups`, in the order people see them: `name` (1 to 80 characters, no control character, no `/`; unique in the project compared case-folded), `origin` and `pins`. `origin` is `{"kind": "plan", "producer", "calls"}` for data the plan window downloaded: the producer's calls of that run in their order, 1 to 1,000 (`MAX_JOB_CALLS`), each `{"command", "options"}` with the options in the JSON form of the producer's catalog (KB-2, ADR-034); or `{"kind": "local", "selections"}` for versions the store already held: each request that added pins to the group appended `{"from": "local_state" | "catalog" | "file"}` with the parameters of `GET /slots` that chose them as `query` (none for `file`). A selection is a record for people, never run again.
   - A pin: `producer`; `version`, the version's file relative to the producer's directory of the store (`/`-separated, no `..`; never a standard path: a link moves to a newer version, a version does not); `sha256`; `content_sha256` when the version's metadata has one (IMGWTools' canonical content, ČHMÚ; `EntryMeta.content_sha256`), else left out; `size_bytes`; `unit` and `label` (`null` when the version has none); `pinned_at` and `pinned_by`. A group pins a version once (producer and `version`); any number of groups and projects pin the same version. A plan group's pins are of its origin's producer; a local group may hold pins of several producers. At most 10,000 pins in a group (`MAX_GROUP_PINS`) and 32 MiB in the file (`MAX_PROJECT_FILE_BYTES`).
   - Not in the file: who sees and changes the project (the state database, A-ADR-029), the own-data folder (Archiwista's settings, A-ADR-027), states of pins (the index) and the activity (the action log, decision 14).

2. **Reading and schema versions.** `archiwista.projects` reads the file, never a producer. A `schema` of `archiwista-project/1` is read: a reader ignores members it does not know, and a writer keeps them (H). `archiwista-project/<n>` with `n` above 1 is a project in a newer format: listed with its `name` when it has one, with the problem `unsupported_project_schema`, its groups not read, every change refused (`409 conflict`, reason `unsupported_project_schema`, the hint to update Archiwista). Anything else, a file that is no JSON object, a member of the wrong type or outside its rule, a file above `MAX_PROJECT_FILE_BYTES` or one that cannot be read is an invalid project: listed by its directory's name with the problem `invalid_project_file` and the JSON pointer and rule that failed, nothing of it read, every change refused (`409 conflict`, reason `invalid_project_file`): Archiwista never writes over a file it cannot read. A pin whose producer has no entry in `stores` is read with the state `unknown`.

3. **Writing: the lock and the atomic replace.** Every change takes the lock `.archiwista-project.lock`, a directory made with `os.mkdir` beside the file (atomic on a local disk and on SMB), and writes `owner` in it (`<host>_<pid>` of `sandbox.process_owner` and the time) for the person who finds it. A lock held by another writer is waited for up to 5 s, then the change is refused: `409 conflict`, reason `project_locked`, `details.lock` the lock's path, the hint `fix.project_locked`. Archiwista never removes a lock (as ADR-040 decided for Kartograf's): a lock stays only when a process dies in the milliseconds of a write, and only a person can tell that no program still changes the project; the message names the owner and, when it is a process of this computer that has ended, says so. Under the lock the writer reads the file again, applies one change to its JSON document (members it does not know stay), validates the result as decision 2 reads it, writes `.archiwista-project.json.<host>_<pid>_<token>.tmp` beside it, `fsync`s it, replaces the file with `os.replace`, `fsync`s the directory where the platform allows, and removes its lock. The changes are: create the file; set `name` and `description`; set or clear `area`; add a producer's store or replace its `root`; add a group; add pins to a local group; replace a group's pins (a re-pin); remove pins of a group; remove a group. A failed write (a read-only share, no space) is `io_error`, reason `project_file_write_failed`, and leaves the file as it was. Then the project is read again into the index in the same process (`record_project`), so the answer shows the change.

4. **The area.** A project's area is one polygon or multipolygon in WGS84, the area of the index chosen on the map (`POST /areas`, its `id`). Archiwista writes it into the project's `obszary/` as `<area id>.geojson` (a GeoJSON `FeatureCollection` of one feature with the properties `name`, `source`, `area_km2` and `countries`; RFC 7946), atomically (a temporary file, then `os.replace`; an existing file of the same name and content is kept), and records its path and the SHA-256 of its bytes in the file. A file of another area is never overwritten or removed. When the project is indexed, its area file is read as JSON (at most `AREA_BODY_LIMIT_BYTES`, the vertex and length limits of `areas.area_from_geometry`; no GDAL, so no worker process is needed) and kept as an area of the index (`areas`, its id the digest of the geometry), so the map shows it by its `area_id`. The area's state is `ok`, `missing` (no file), `changed` (other bytes than `sha256`: not used) or `invalid` (not a polygon in WGS84, or over a limit).

5. **Discovery and the index.** The configured project directories are searched for `archiwista-project.json` only, by the rules of today's discovery (at most `MAX_PROJECT_DEPTH` = 4 levels below a project directory, no hidden directory, no store's producer directory, a file that is a symbolic link resolving outside the project directory is invalid with `path_outside_root`). A directory with only `kartograf-project.json` or `imgw-project.json` is no project, and nothing reads or mentions those files (D4). Discovery runs with the scan of a store, as today, and needs no producer: only a file whose modification time or size changed since it was indexed is read again. The index (rebuildable; `SCHEMA_VERSION` 15) keeps:
   - `projects`: `key` (made from the name when the file is first indexed and kept while the directory holds one, as today), `path`, `access_key` (the directory after `realpath`, the key of the state database), `name`, `description`, `state` (`ok`, `invalid`, `unsupported_schema`), `problem` and `problem_detail` (the reason and its pointer, rendered at each request in the language asked), `created_at`, `created_by`, the area (`area_path`, `area_sha256`, `area_id`, `area_state`), the file's `mtime_ns` and `size`, `scanned_at`;
   - `project_stores`: per project and producer, the `root` as written and the configured store it matches by resolved path or alias as today, else none ("Magazyn projektu nieznany: dodaj magazyn");
   - `pin_groups`: per project, `position`, `name`, `origin` (`plan`, `local`), `producer`, `calls` and `selections` (JSON);
   - `pins`: per project and group, `producer`, the matched `store_id`, `version_path`, `sha256`, `content_sha256`, `size_bytes`, `unit`, `label`, `pinned_at`, `pinned_by`; joined with `versions` by store and path, so a pin's state is `ok`, `missing` (no present version at its path), `sha256_mismatch` or `unknown` (its producer's store is not configured), as today.

   `versions` gains `content_sha256` (from `EntryMeta`). The tables `manifests` and `project_tasks` go. "Przypięta w:" of the file card names the project and the group; the report of versions no project uses, the `project` filters of `GET /slots`, `GET /map/footprints`, `GET /jobs` and `POST /previews/warm`, the search of project names (now with the names of groups) and the visibility of all of them (A-ADR-029) read these tables as they read the old ones.

6. **Where a project lies, who creates and changes it.** The rules of ADR-039 decision 3 and its erratum 3 stay, restated here: a new project's path is absolute, equal to or below a configured project directory that exists, at most `MAX_PROJECT_DEPTH` levels down, in no hidden directory and no store's producer directory, and the part of it that exists resolves inside the project directory (`403 forbidden` `path_outside_root`; `400 validation_error` `project_not_discoverable` or `project_dir_missing`); a missing directory is made. Any signed-in person, or their agent, creates a project where none is (`project.create`) and owns it: an access entry with that owner and the visibility of `default_project_visibility`, logged as `project.create`; the local owner creates one without an access entry, as before. A directory that holds `archiwista-project.json` is a project already (`409 conflict`, reason `project_exists`); a directory with an access entry and no file is created again by its owner or an administrator only (`project.write`). Every change of a project (decision 3's changes, the jobs that write, the exports) needs `project.write` (its owner or an administrator) after the visibility check (`404` for a project the session does not see, `403 permission_denied` for one it sees but may not change).

7. **The stores of a project.** A project names no store when it is created. The first pin of a producer adds that producer's entry with the configured store of the pinned version (`root` written as decision 1 says). A pin of a version from another configured store than the one the project names for its producer is refused (`409 conflict`, reason `other_store`, `details.store`), as is a pin while the project's store of that producer matches no configured store (`409 conflict`, reason `unknown_store`). The project's owner moves a producer's entry to another configured store (`PUT /projects/{project}/stores/{producer}`; `project.store` in the log), for a store that moved or is mounted at another path: the pins are relative to the store, so they stay (KH-1 of SPEC 12.6 is withdrawn: Archiwista writes the file).

8. **Pinning what the store holds (origin `local`).** No network and no producer: the versions and their `sha256`, `content_sha256`, size, unit and label come from the index. A request names its versions, or the query of `GET /slots` that the Catalog and "Stan lokalny" use (the rows' versions, `current` by default, through every page). "Dodaj do projektu…" of "Stan lokalny" (the area, a product and the filters of the map: year, variant), of the Catalog (its current result) and of the file card (the version chosen on its timeline, older ones too) opens one dialog: a project the session may change, then a new group's name or a local group of that project. A version that is not present, or has no `sha256`, is not pinned and is listed with its reason (`missing`, `no_sha256`); a version a group pins already is counted, not added twice; a request above `MAX_GROUP_PINS` is refused before anything is written (`400 validation_error`, reason `too_many_pins`, `details.count`). Pins are added to a group of origin `local` only (`409 conflict`, reason `group_origin_plan`).

9. **Pinning new data from the plan window (origin `plan`, J).** "Dodaj jako zadanie projektu" becomes "Dodaj do projektu": a project the session may change and a new group's name. The window's download (`POST /jobs`, kind `download`, its `calls` and `plan_job`) carries `pin: {"project", "group"}`; the request asks `project.write` besides `store.write` and refuses a taken group name (`409 conflict`, reason `group_exists`) before a job exists, and a retry asks the same. When the job succeeds, its worker writes the group: origin `plan` with the job's producer and calls, a pin for every file of its `files[]` (DEV-19.19: `version_path`, `sha256`, `size_bytes`, `label`, `unit`; `content_sha256` from the index after the rescan), and for every position of the call's kept plan the run did not transfer (`current`, a `newer` one kept, a position another job fetched) the version the index holds at its standard path after the rescan. A position no version of the store answers is listed in the result as not pinned (`not_in_store`). A job that ends `partial` or fails pins nothing (a group is written only from a whole run, as a re-pin), and its result says so; a pin that cannot be written (the lock, a changed project, a name taken meanwhile) leaves the downloaded data and ends the job `partial` with `pin.error`. The plan window offers the option for the session's projects with `project_write`, for a row of any number of lines (the restriction to one command of ADR-042 decision 3 goes); without the network there is no plan, so the option is disabled with the reason. ADR-047's claims and the plan the person saw apply unchanged.

10. **The source interface.** `ProjectActionAdapter`, `SourceAdapter.read_project` and `project_status`, and the types `ProjectInfo`, `ProjectTask`, `ProjectPin`, `ProjectRun`, `ProjectTaskRun`, `PinnedVersion`, `ProjectCheck`, `ProjectFileState`, `TASK_OUTCOMES` and `PROJECT_FILE_STATUSES` go, and with them the adapters' project functions and `kartograf-project/1` and `imgw-project/1` from the adapters' `SCHEMAS`. One optional capability comes: `VersionCommandAdapter.command_for_version(version: str, *, root: Path) -> CommandCall`, the call that selects the stored version `version` (a path relative to `root`, the configured store's producer directory), offline and read-only: Kartograf's `command_for_file` with the version's sidecar, IMGWTools' `command_for_version(version, root=root)`. The producer's coded refusal (`unsupported`, `command_not_rebuildable`) becomes `UnsupportedError` with the reason `command_not_rebuildable` and the producer's text unchanged (as `ActionAdapter.check` raises `no_plan`); any other refusal is `ProducerError`. `ActionAdapter.run` gains `upgrade: bool = False`, the producer's update mode without a plan (Kartograf `update="upgrade"`; a producer without one refuses it with `UnsupportedError`, reason `no_upgrade`). The answers of `command_for_version` are cached in the index per version (`version_calls`: store, version path, the producer's version, the call or the refusal's text; `SCHEMA_VERSION` 16): a version is immutable, so its answer changes only with the producer. A local pin service fills it for the pins it adds and every project job for the pins it reads; the card only reads it, so its pins show `rebuildable`, `not_rebuildable` with the text, or `unknown`. The file card's "Polecenie Kartografa" (and an IMGW version's command) is `GET /stores/{store}/versions/{version}/command`: the call and its line (`ActionAdapter.format`, `null` for a producer without commands), or `422 unsupported` with `command_not_rebuildable` or `no_commands`.

11. **The jobs.** Four kinds, each over the groups a request names (`groups`, every group when left out; a name given twice kept once) of one project, started by `POST /projects/{project}/jobs` (`kind`: `verify`, `check`, `repin`, `restore`), with no configured store of their own (`store` `null`) and the parameters `project` and `groups`. They share the conflict domain `project` (one job of a project at a time, `409 conflict` with the job in the way in `details.job`), as ADR-040 decision 4 did; who sees the project sees the job.
    - `project_verify` (no network; `project.view`): reads each pinned version's file inside its store root (no symbolic link out) and hashes it: `ok`; `corrupt` (other bytes); `missing`, unless the index holds a present version of the pin's slot whose `content_sha256` equals the pin's, then `content_match` with that version; `no_store` for a pin whose store is not configured. A store that cannot be read fails the job with `store_unavailable`. It succeeds with `ok` false when it found problems, and changes nothing.
    - `project_check` (network; `project.view`): asks the source through `ActionAdapter.check` and writes nothing but the producer's metadata cache. A plan group is checked by its calls; a local group by the call of each pin (`command_for_version`, the same call asked once). Each pin is compared by its slot (the standard path of its version) and `sha256`, never by a count: `current` (the source has nothing newer and the store's current version of the slot is the pinned one), `newer` (the source has a newer version, or the store's current version is another one; the label shown), `missing` (the pinned version is gone from the store), `removed` (the call no longer selects the slot), `unverifiable`, `check_failed`, or `not_checkable` (a local pin without a call, with the producer's reason: D5); a position of a plan group's calls without a pin is `added`. A mismatch is reported, never re-pinned. It ends `partial` when some pins could not be asked, and fails (`CheckFailedError`) when none could.
    - `project_repin` (network; `project.write` and `store.write`; exactly one group): runs the group's calls (a local group: the calls of its pins) with `upgrade=True`; when every call and every unit succeeded, the group's pins are replaced under the lock: a plan group's by the files of the runs, a local group's each by the file of the run at its slot; a pin whose version did not change keeps its `pinned_at` and `pinned_by`, the others get the job's actor and time. Anything less than a whole success changes no pin (the downloaded versions stay in the store); a local group with a pin without a call cannot be re-pinned (disabled with the reason, refused with `422 unsupported`, `command_not_rebuildable`).
    - `project_restore` (network; `project.write` and `store.write`), the former `project_download`: for the groups with pins whose version is missing from the store, runs their calls in the producer's default mode (the versions the store holds are kept); a missing pin whose `sha256` returns is `restored`, one whose `content_sha256` returns with other bytes is `content_match` (kept, shown apart from `restored`, never re-pinned silently, A-ADR-023 erratum 2), any other is `not_restored` with the reason `other_content` or `not_returned`; a local pin without a call is `not_restorable` with the producer's reason (D5). It never writes the file. It ends `partial` when some missing pins were not restored and fails when none was.
    - The jobs that run calls need the producer's commands (`ActionAdapter`): a group whose producer has none (IMGWTools until its actions come with v0.5) is refused before a job (`422 unsupported`, reason `no_commands`) and shown disabled with that reason. `project_check`, `project_repin` and `project_restore` need the network (`409 offline_mode` in offline mode); their store is the project's store of the group's producer, which must be configured (`409 conflict`, `unknown_store`) and readable (`503 store_unavailable`). After a run the slots of its files are read again, and after an interruption the slots its progress named, as a `download` job does (ADR-037). The results keep every pin and file with its state, so a large project makes a large result (as ADR-040 said). The kinds of ADR-040 go and these four come, each change raising `PROTOCOL_VERSION`; `project_download` has no successor of that name.

12. **Versions whose command cannot be rebuilt (D5).** They are pinned like any other (decision 8). Their check and restore are not attempted; the job reports them as `not_checkable` or `not_restorable` with the producer's text, and their group cannot be re-pinned. The card disables "Sprawdź aktualizacje", "Przywróć brakujące" and "Przepnij" of a local group with the reason when the index knows that no pin of it has a call (`version_calls`), and shows the reason at each such pin. A later sidecar field recording the inputs of derived data lifts it per family, in the producer, with no change here.

13. **Exports (D6).** "Eksportuj…" of the card writes `zestawy/<name>/` in the project's directory (`name` of 1 to 64 characters of letters, digits, `.`, `_` and `-`, not starting with `.`): `pliki.txt`, one pinned version's file per line in the order of groups and pins, each pin once (a version pinned by two groups is listed once): relative to the export directory when that and the version file have a common directory below the file system's root or drive (the same share), else absolute, as the server reads it; `ATRYBUCJE.txt`, the attribution texts of the pinned versions (`versions.attribution` of the index, from the sidecars' `license.attribution`) without repetitions, in the order of their first pin. Both UTF-8 with LF; a pin whose store is not configured, or whose version is not present, is left out and counted. Regenerating replaces each file atomically; Archiwista never removes an export. An export is a change of the project (`project.write`, `project.export` in the log). The list of a project's exports says when the project file changed after an export (its modification time after the export's), so people regenerate it. The QGIS project, `pliki.csv`, `polecenia.sh`, `vrt/`, `szeregi/` and the description `zestaw.json` (SPEC 8.4) are v1.1.

14. **Activity (D7).** A project's activity is the action log (A-ADR-047): its entries `project.*` whose target is the project's access key, and the entries `job.start`, `job.retry` and `job.cancel` whose `details.project` is the project's key (a project job, or a `download` that pins into it: its `pin.project`), with the outcome `ok` or `failed`, newest first, with a cursor. `GET /projects/{project}/activity` answers it to whoever sees the project, without the client address and the session, which stay the administrators' (`GET /log`). No history file is written in the project's directory (D7 b is rejected: only for projects that must carry their history to another installation).

15. **The names of the log.** New: `project.update` (name, description), `project.area`, `project.store`, `project.pin` (details: group, origin, the pins added and skipped), `project.unpin` (group, pins removed, or the whole group) and `project.export` (name, pins), each with the project's access key as target. `project.create`, `project.access` and `project.data_dir` stay; `project.task_add` and `project.task_remove` go (never released).

16. **The routes and commands.** `GET /projects` (`?store=`: projects whose store entry matches the store), `POST /projects` (`path`; `name`, by default the directory's name; `description`; `area_id`), `GET /projects/{project}`, `PATCH /projects/{project}` (`name`, `description`), `PUT /projects/{project}/area` (`area_id` or `null`), `PUT /projects/{project}/stores/{producer}` (`store`), `POST /projects/{project}/groups` (a new local group), `POST /projects/{project}/groups/{group}/pins` (pins added to a local group), `POST /projects/{project}/groups/{group}/unpin` (pins removed), `DELETE /projects/{project}/groups/{group}`, `POST /projects/{project}/jobs`, `GET /projects/{project}/activity`, `POST` and `GET /projects/{project}/exports`, `GET /stores/{store}/versions/{version}/command`, and `pin` of `POST /jobs`; with the commands `archiwista project-init`, `project-edit`, `project-area`, `project-store`, `project-pin`, `project-unpin`, `project-verify`, `project-check`, `project-repin`, `project-restore`, `project-activity`, `project-export`, `project-exports`, `version-command` and `jobs start download … --pin PROJEKT --pin-group GRUPA`, each the route's model with `--json`. `GET /projects/{project}/status`, `POST /projects/{project}/tasks`, `DELETE /projects/{project}/tasks/{name}`, `archiwista project-add`, `project-remove`, `project-status` and `project-download` go without an alias. The plan's phases give each route's model and refusals.

**Consequences:**
- A pin names a version and its `sha256`, so many projects pin one version, data the store holds is pinned offline in one step, and an older version chosen in the file card is pinnable (SPEC 15 P9 resolved). A store written meanwhile by another process changes no pin.
- The project file is the source of truth of a project, as the sidecars are of the store: the index rebuilds from it, it travels with the directory, and a lost state database loses only access entries (as before). The producers' manifests are no longer read; a directory holding only one is no project (D4).
- Archiwista writes one more kind of user data on a share: the project file under its lock, the area files and the exports (CLAUDE.md, SPEC 1.3 and 10.1 name them). A lock left by a killed process is removed by a person, as before.
- Without the producer's CLI a project cannot be rebuilt by the producer alone: `archiwista project-restore` does it, and `polecenia.sh` comes with the QGIS export (v1.1).
- The command of a local version may select more or other data than the version (a newer campaign, another height system): the check compares by slot and `sha256`, never by count, and reports a mismatch.
- IMGWTools has no actions in Archiwista yet (v0.5): IMGW versions are pinned, verified and exported, and their check, re-pin and restore wait for its commands, disabled with the reason.
- The HTTP API and the command line change without aliases (none of them was released, D2); the index rebuilds twice during the work (`SCHEMA_VERSION` 15 and 16), once for a person updating from the last release.
- Tests: the generated store's projects become `archiwista-project/1` files (`tests/fixtures/make_store.py`), and `kartograf.testing`'s project builders, which leave with Kartograf's projects, are no longer used.
