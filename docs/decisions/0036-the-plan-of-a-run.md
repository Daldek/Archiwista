# ADR-036: The plan of a run: a `check` job, the plan kept with it, the state `partial`

**Date:** 2026-10-25
**Status:** proposed (done on the topic branch `feature/kartograf-data-output`, step A4 of the plan `docs/plans/2026-10-25-archiwista-next.md`, whose approval is delegated; accepted when the author approves and merges the branch)

**Context:** Every network or write action goes through the plan window (SPEC 13 v0.3, criterion 4): before a download runs, the person sees what it would do in the store: the files that are current, newer at the source, missing or impossible to verify, their labels, the size, the target store and the producer's own command line. Kartograf plans a run without effects with `check_command(command, options, *, root, cache, on_notice)`, whose envelope `kartograf-result/1` holds `kartograf-plan/1` (`UpdatePlan`: positions with `status` `current`, `newer`, `missing`, `unverifiable` or `check_failed`, the local and the available label, `store_path`, the producer's signal of the available version; no size, KC-3), and a run with `update="upgrade", plan=…` executes exactly that plan later, so the plan must survive until the person decides. A plan of many sheets is large, and one position the source does not answer for does not make the rest of the plan useless (Kartograf's envelope is then `partial`, not `failed`). IMGWTools has the same call shape (`check_command(command, /, *, options)` with `root` in `options`, `imgw-plan/1`).

**Options:**
- A) The plan in the job's result. Rejected: `GET /jobs` lists every job with its result, so each list would carry every plan's positions, and the producer's own plan (needed by the run of the plan) would be in it twice.
- B) A table `plans` of the index keyed by the job, deleted with the job; the job's result holds the summary (counts, size, the line, the store). The run of a plan reads the producer's plan back from it.
- C) A file per plan in the jobs directory. Rejected: a second place to prune, and nothing reads it but Archiwista.

**Decision:** B.

1. **Capability** (`sources/protocol.py`). `ActionAdapter` gains `check(command, options, *, root, on_notice)`, which returns the producer-neutral `ActionPlan` (`sources/types.py`): `producer`, `command`, the schema of the producer's plan, the `root` it is of, `checked_at`, the `entries` (`PlanEntry`: `path` below the store root, `unit`, `status`, `local_label`, `available_label`, `size_bytes`, `error`, `conflict`), the notices and the producer's plan itself as JSON (`document`). `ok`, `counts()`, `todo` (the positions a run downloads: `newer`, `missing`), `size_bytes` and `size_complete` are read from the entries. The Kartograf adapter calls `check_command` with `root=` the configured store's directory and Archiwista's own `MetadataCache` (D5); a root a write would refuse (`nested_store`, `not_empty`) is the plan's one position with its reason in `conflict`; a check that answers with no plan of a store (`project download`, A8) is `422 unsupported` (`no_plan`).
2. **Size.** A size the producer does not tell is `None`, never 0. `size_bytes` of a plan is the sum of the known sizes of the positions to download, `None` when none of them is known, and `size_complete` says whether every one is; a plan with nothing to download is 0 and complete. Kartograf's plan names no size (KC-3); the `content_length` of a position's signal is the size of a transfer, which for a packed source is not the file in the store, so it is not taken.
3. **The job** `check` (`JobRule(store=True, network=True)`): parameters `producer`, `command`, `options`; offline mode refuses it before it is recorded (`409 offline_mode`). The worker takes the producer directory of the job's store (`services.commands.store_root`), passes the producer's notices on as job notices and keeps the plan in the index table `plans` (`SCHEMA_VERSION` 9: the index is rebuilt, SPEC 4.4) with the store and the producer's command line of the run (`format`, with the store's root). The job's result is the summary: `producer`, `command`, `store`, `root`, `line`, `checked_at`, `ok`, `positions`, `counts`, `size_bytes`, `size_complete`, `failed` and `seconds`.
4. **The state `partial`.** A job may end `partial`: it did part of its work and its summary names what failed. The worker's runner returns `PartialResult(summary)`, the worker sends the message `partial` instead of `result` (`PROTOCOL_VERSION` 6), the supervisor keeps the summary as for `succeeded` and records no error; the jobs table allows the state, it is a final state everywhere (the API, `FINISHED_STATES`, the interface) and the exit status of a command following such a job is 10 (ERR §1). A plan some of whose positions are `check_failed` ends `partial`; a plan with none checked fails the job (`source_unavailable`, reason `check_failed`, the producer's text of the first) and is not kept.

**Consequences:**
- The plan window (A11) reads the summary from `GET /jobs/{job}` and the positions from the kept plan; a later download of the plan (A5) gives the producer its own plan back from `ActionPlan.document`.
- A plan lives as long as its job: 90 days, and the last finished `check` of a store stays (`prune`).
- A client that lists final states must add `partial`; the interface treats it as finished, with the colours of a warning.
- Kartograf's plan needs the network, so the parity of a plan with the CLI is the live test of A14; offline the conversion is shown on `store init`, whose plan needs no network.

**Erratum 1 (2026-10-26, the author's problem: "Pobierz…" waited on the source again right after "Sprawdź u źródła"):** the check asked GUGiK again for what the availability report had just learned: Kartograf's check refreshed the metadata cache (every read a miss) and the report's cached answers were not the entries the check read (measured on Kartograf's recorded answers: 7 requests for a 6-sheet hint, 16 for 15 sheets, 288 for the 34 hints of a Kraków report). Kartograf ADR-056 shares one cached index answer between the report and the plans and gives the cache a TTL of refresh mode; the adapter's `check` opens its cache with `refresh_ttl_seconds=PLAN_REFRESH_TTL_S` (3600): an answer of the source younger than an hour stands for asking it again, so the plan of a row of a report checked within the hour asks GUGiK nothing and plans the same positions. A row of an older report, a pasted line whose sheets the cache does not hold, the CZ part (one `HEAD` per file) and every run (`--upgrade` refreshes) still ask. The wait that stays is one worker process per line, two at a time (ADR-007, ADR-035 point 6): about 0.9 s of imports and 0.5 s of bookkeeping per line, measured 2026-10-26; whether a row's lines are planned in one job is the author's decision.

**Erratum 2 (2026-10-26, ADR-044):** a `check` job takes `calls[]` and keeps one plan per call (`plans` keyed by job and `call`, `SCHEMA_VERSION` 12); it ends `partial` when some call or position could not be checked and fails only when no call was planned.
