# ADR-046: Team mode: sign-in, sessions and transport security

**Date:** 2026-10-26
**Status:** accepted (delegated approval: on 2026-10-26 the author delegated the decisions of v0.4 to the coordinating session with the rule "follow the SPEC and the ADRs; where something is missing choose security first, teamwork second, the state of the art without over-engineering"; to be built by the plan `docs/plans/2026-10-26-plan-v0.4.md`, steps T1 to T5; amends ADR-012 and ADR-013 for team mode)

**Context:** v0.4 opens the server to the local network (ADR-013, SPEC 10.2). Since v0.1 the server listens on `127.0.0.1` only, and a session starts from a one-time token in the address that `archiwista serve` prints (ADR-012); the permission model knows accounts, groups and roles (ADR-029), but no account can sign in. SPEC 10.2 named local accounts with Argon2id passwords, authentication by a reverse proxy, optional groups from LDAP/AD and mandatory TLS. It left open how the first administrator appears, how a person gets and changes a password, how long a session lives and how it ends, what stops password guessing, when the header of a proxy is believed, and on which conditions the server may listen beyond the loopback address.

**Options:**
- Sign-in: A) local accounts with Argon2id passwords, and optionally a reverse proxy that names the person in a header; B) Archiwista binds to LDAP/AD itself; C) OpenID Connect in Archiwista.
- Groups: D) managed in Archiwista; E) read from LDAP/AD.
- Sessions: F) kept in the server's memory, with a revocation time per account in the state database; G) kept in the state database; H) signed tokens without server state.
- Transport: I) TLS in the server (certificate and key files) or a trusted reverse proxy with TLS, nothing else; J) TLS recommended, optional on a local network.
- First administrator: K) created with the command line on the server; L) a setup page in the browser.
- Guessing: M) a growing wait per account name and per client address; N) a lock until an administrator unlocks the account; O) a CAPTCHA.

**Decision:** A, D, F, I, K and M.

1. **Team mode** is an explicit setting, the table `[team]` of `config.toml`: `enabled`, `origin` (the `https` address people open: scheme, host and optional port, no path), `tls_cert` and `tls_key` (both or neither), `trusted_proxies` (addresses, or networks of at most 256 addresses), `proxy_user_header` and `proxy_autocreate`. The server reads it when it starts; `GET /settings` does not show it and `PUT /settings` keeps it as it is, so no session can widen the server's exposure. Local mode (the table off) stays as ADR-012 describes it.
2. **Listening.** `archiwista serve --host ADDRESS` listens beyond `127.0.0.1` only in team mode, and only (a) with TLS in the server, both files loaded before anything binds, or (b) with `trusted_proxies` and a specific address (not `0.0.0.0` or `::`), which must be a loopback address when every trusted proxy is one. In team mode the server also refuses to start without an enabled administrator who can sign in (a usable password, or the proxy header configured). Each refusal is exit 2 (`validation_error`) with its reason (`host_refused`, `tls_required`, `tls_unusable`, `proxy_bind_wildcard`, `proxy_bind_not_loopback`, `team_no_admin`) and a hint, before the port is bound.
3. **Transport.** In team mode every request comes over TLS: directly, or from a trusted proxy whose last `X-Forwarded-Proto` is `https`. Any other request answers `403 forbidden` (reason `tls_required`), and without TLS in the server a peer that is not a trusted proxy answers `403` (reason `proxy_required`). The `Host` rule and the `Origin` rule of ADR-012 compare with `origin`; `X-Forwarded-Host` is never read, so the proxy keeps `Host`. The client address of the logs, the limits and the sessions is the peer, or behind a trusted proxy the right-most `X-Forwarded-For` address that is no trusted proxy. Every response carries `Strict-Transport-Security: max-age=31536000` (ASVS 3.4.1; without `includeSubDomains`, which could break other services of the network's domain). `/api/docs` is not served (SPEC 9.1). There is no startup token and no launch file: people sign in.
4. **Accounts and passwords.** A password is kept as an Argon2id hash (argon2-cffi with its defaults, the second recommended option of RFC 9106: 64 MiB, 3 passes, 4 lanes; a hash of weaker parameters is replaced at the next sign-in) in a table of its own that only the password module reads; no answer, log or error shows a hash. A password is normalised to NFKC and has 12 to 1,024 characters of any composition; it may not be the account's id or name (ignoring case) or one of the 3,000 most common passwords of 12 characters or more (a list in the package with its source and licence; ASVS 6.2.4). Nothing forces a periodic change. The first administrator is created at the server's terminal: `archiwista users add ID --role admin`, then `archiwista users password ID`; there is no setup page. An administrator gives a person a temporary password that the server generates (about 90 bits, shown once, valid 72 hours; ASVS 6.4.1); the person must change it at the first sign-in, and until then the session may only read itself, change the password and sign out (`403`, reason `password_change_required`). `archiwista users password ID [--temporary]` sets a typed one at the terminal. The last enabled administrator cannot be removed, disabled or deprived of the role (`409 conflict`, reason `last_admin`).
5. **Sign-in.** `POST /api/v1/session/login` (account and password) answers like the token exchange: a session cookie and the session's CSRF token. An unknown account, a wrong password, a disabled account and an account without a password all answer `401` with the reason `login_failed` and the same text, after the same work (the password is verified against a stand-in hash when there is no hash to verify), so no answer tells whether an account exists (ASVS 6.3.8). A correct temporary password past its end answers `401` with the reason `password_expired`. At most two hashes are computed at once (each takes 64 MiB); the other sign-ins wait.
6. **Guessing (M).** After five failed sign-ins of one account name, or from one client address, each further attempt is refused without checking the password (`429 rate_limited` with `Retry-After`) for 1, 2, 4… seconds, up to 15 minutes; a success clears both counts. The counts live in the server's memory: a restart, which only the server's operator can cause, clears them, and the action log keeps every failure (ADR-047). N was rejected because anyone could keep a colleague out until an administrator acts; O needs an external service or a weak home-made puzzle. The wait per account name can still delay a colleague's sign-in by up to 15 minutes; the action log shows who tried, from where (ASVS 6.1.1).
7. **Sessions (F).** A sign-in, a token exchange and a password change always start a new session (a random 256-bit id kept as its SHA-256 hash) and end the session whose cookie the request carried (no fixation, ASVS 7.2.4). The cookie of team mode is `__Host-archiwista_session`: `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/` (ASVS 3.3.1); the cookie of local mode keeps its name. Every `/api` request still carries the session's CSRF token in `X-Archiwista-CSRF` (ADR-012 erratum 2). A session ends after 8 hours without a request and 7 days after its start (an agent's 12 hours after), at sign-out, when its account is disabled or removed, and when the account's revocation time passes its start: a password change (the new session excepted), "Zakończ sesje" of an administrator (`DELETE /users/{id}/sessions`) and `archiwista users end-sessions ID` set it, so a command at the terminal ends the sessions of a running server. A person lists their live sessions and ends any of them (`GET /sessions`, `DELETE /sessions/{label}`). G was rejected: sessions that survive a restart cost a write per request for a rare event; H cannot be revoked without server state.
8. **Reverse proxy (optional).** With `proxy_user_header`, a request from a trusted proxy carrying the header with an account id starts a session as that person (`POST /api/v1/session/proxy`); the account must exist and be enabled or, with `proxy_autocreate`, is created without roles. Every later request of that session must come from a trusted proxy with the same value, else the session ends. The header from any other address is ignored and logged (once an hour per address). The proxy authenticates as it likes (SSO, Kerberos or LDAP against Active Directory) and must replace any such header a client sent.
9. **Groups (D); LDAP/AD deferred (E).** Groups stay local (the API, the command line and the screen of v0.4). Groups from LDAP/AD would need a directory client, the directory's credentials stored on the server, TLS to the directory and rules for groups that exist in both places: a surface of its own for little gain, since a team of a few people keeps a few groups by hand and the proxy already brings sign-in against AD. B and C were rejected for the same reason: the proxy is the path to SSO and AD (SCOPE, "Out of the MVP").
10. **Agents.** An agent's token belongs to the account that issued it and acts with that account's roles (ADR-012 erratum 2). In team mode `POST /session/tokens` gives an address of `origin`, and `archiwista token --user ID` issues one at the server's terminal for an account.

**Consequences:**
- New dependency `argon2-cffi`; the state database gains the table `passwords` and the accounts' revocation time (state schema version 3, together with the action log of ADR-047).
- A restart of the server signs everyone out; the operator restarts rarely, and the revocations of the command line need no restart.
- With a proxy on the server's own machine, every account of that machine can connect as the proxy and forge the header: the LAN runbook asks for a machine without other accounts, or TLS in Archiwista without the header.
- `/api/docs` stays a feature of local mode; `/api/v1/openapi.json` stays behind a session.
- The requirements of OWASP ASVS 5.0 level 1 for authentication and sessions are met by design; the review checklist is `docs/reports/v0.4-security-checklist.md` (plan step T12).
