# ADR-040: The jobs of a project: download, repin, check, verify, and the left lock

**Date:** 2026-10-26
**Status:** proposed (done on the topic branch `feature/kartograf-data-output`, step A8 of the plan `docs/plans/2026-10-25-archiwista-next.md`, whose approval is delegated; accepted when the author approves and merges the branch)

**Context:** v0.3 "Actions" runs a project's tasks (SPEC 4.7, 5.6, 9.2; the plan's A8; the project actions of the interface, A13): download and pin what a task names, restore a missing pinned version, repin one task to the source's newer versions, compare the pins with the source and verify the pinned files. Kartograf offers `download_project(project_dir, *, tasks, update, cache, on_progress, on_notice)`, `check_project(…, cache, on_notice)` and `verify_project(…)` in `kartograf.__all__`; its `ProjectReport` (`kartograf-project-report/1`) and `ProjectCheck` (`kartograf-project-check/1`) keep the pins' paths relative to the store. Unlike `run_command`, these calls take no store: Kartograf writes the store the manifest names. Kartograf writes a manifest under a lock, the directory `.kartograf-project.lock` beside it (its `LOCK_NAME`, not in `kartograf.__all__`), taken only to commit a task's pins or to add or remove a task; after a 5 s wait it refuses with `ValidationError` and the text `project.project_locked`, no reason. A lock stays only when the process holding it is killed during the milliseconds of a write (SPEC 5.6), and Kartograf's text says to remove it by hand. Open questions: which store a project job writes, how a left lock reaches the person, how the jobs share a project, and who may start which job.

**Options:**
- Calls:
  - A) `run_command("project download", …)`. Rejected: its envelope holds the producer's report without the classes and offers no `check_project`; the run of a project's tasks has its own calls in `kartograf.__all__`.
  - B) The library functions behind an extension of `ProjectActionAdapter` with producer-neutral types.
- The store:
  - C) Whatever store the manifest names. Rejected: Archiwista writes only configured stores (the plan, rule 1).
  - D) The configured store the manifest names, matched as a scan matches it, after the manifest is read again (SPEC 4.7: a manifest changed meanwhile is read again before every action).
- The left lock:
  - E) Kartograf's refusal as it is (`400 validation_error`). Rejected: the person gets no path and no instruction in Archiwista's terms, and nothing tells a left lock from an invalid manifest.
  - F) Remove the lock when it is older than some age. Rejected: only the producer knows whether a process holds it, and SPEC 5.6 leaves its removal to a person.
  - G) Name it: a refusal, or a failed task, while the lock stays is `409 conflict`, reason `project_locked`, `details.lock` and the instruction; Archiwista never removes it.
- Sharing a project:
  - H) Queue a second job of a project behind the first. Not now: the supervisor's queue knows kinds and network slots, not projects.
  - I) Refuse it, as a second job writing a store's index is refused (`JobConflict`).

**Decision:** B, D, G and I.

1. **Capability** (`sources/protocol.py`, `sources/types.py`). `ProjectActionAdapter` gains `download_project(directory, *, tasks, upgrade, on_progress, on_notice) -> ProjectRun`, `check_project(directory, *, tasks, on_notice) -> ProjectCheck` and `verify_project(directory, *, tasks) -> ProjectCheck`. `ProjectRun` (`producer`, `root`, `tasks`, `notices`; `ok`, `failed`, `counts`) holds a `ProjectTaskRun` per task (`name`, `outcome` of `TASK_OUTCOMES`: `pinned`, `unchanged`, `restored`, `updated`, `failed`; `pinned` and `unpinned` as `PinnedVersion`: `path`, `version_path` below the store root, `unit`, `label`, `sha256`, `size_bytes`; `errors`, `code`, `reason`). `ProjectCheck` (`producer`, `root`, `files`, `not_downloaded`, `notices`, `ok`; `counts`) holds a `ProjectFileState` per file (`task`, `unit`, `path`, `status` of `PROJECT_FILE_STATUSES`: `ok`, `missing`, `corrupt`, `current`, `newer`, `added`, `removed`, `unverifiable`, `check_failed`, `conflict`; `pinned_label`, `available_label`, `detail`).
2. **Kartograf** (`adapter/kartograf/actions.py`). `download_project` with `update` unset (pin or restore) or `"upgrade"` (a repin), `tasks`, Archiwista's own `MetadataCache` (D5, never `cache=True`) and the converters of a run's progress and notices; `check_project` with the same cache; `verify_project`. Their refusals keep Kartograf's description with the hint of the catalog's `project download` (its check is `project download --check`; there is no `project check`) or `project verify`.
3. **The left lock.** When a call of a project (also A7's `create_project`, `add_project_task`, `remove_project_task`) is refused by Kartograf, or a task of a download fails, while `<project>/.kartograf-project.lock` is a directory, the adapter raises `ProjectLockedError` (`ConflictError`, reason `project_locked`, `details.lock` the path, the hint `fix.project_locked`), its text Kartograf's own after Archiwista's. The lock and the manifest are left as they are. A request to Kartograf for the reason `project_locked` on its error is filed in the plan.
4. **Jobs** (`PROTOCOL_VERSION` 8). The kinds `project_download`, `project_repin`, `project_check` and `project_verify` (`PROJECT_KINDS`) work on no configured store (`store` is `null`); their parameters are `project` (the key) and `tasks` (a list of names, a name given twice kept once, or `null` for every task), a repin exactly one task. Who sees the project sees the job (`params.project`, A-ADR-029). The download, the repin and the check need the network (refused in offline mode); the verification does not. One job of a project at a time: they share the conflict domain `project` (`409 conflict`, the job in the way in `details.job`).
5. **The worker.** A download and a repin read the manifest again into the index (`record_project`), require its store to be a configured store with a directory of the producer (`409 conflict`, reason `unknown_store`, with the fix of the index problem `unknown_store`) that can be read now (`503 store_unavailable`), run the producer, record the project again, and read the slots of the files pinned or unpinned again (`scope`, `refresh_view`); an interrupted or failed run reads again the slots of the units its progress named, as a `download` job does (ADR-037). A run some of whose tasks failed ends `partial`; one all of whose tasks failed fails (`RunFailedError`, the code of the first failed task, `details.task`). A check some of whose pins could not be asked ends `partial`, one with none asked fails (`CheckFailedError`). A verification succeeds with `ok` false when files are missing or corrupt: it found them, so it did its work.
6. **Who** (A8 commit 2). A download and a repin need `project.write` of the project (its owner or an administrator) and `store.write` (SPEC 13 criterion 7); a check and a verification need only to see the project (`project.view`). A project the person does not see is `404`, before anything else.

**Consequences:**
- `POST /projects/{project}/jobs` (`kind`: `download`, `repin`, `check` or `verify`; `tasks`) and `archiwista project-download`, `project-repin`, `project-check` and `project-verify` start these jobs over one service (A8 commit 2); a retry asks the same permissions again.
- A download of a task whose pins the store holds touches neither the network nor the lock (`unchanged`), so it works offline in Kartograf; Archiwista still refuses it in offline mode, as it cannot know before the run.
- A pin deleted from the store, restored offline, fails its task after Kartograf's retries (`conflict`, `pin_mismatch`); a corrupt pin fails it at once (`data_error`, `corrupt_pin`) with Kartograf's remedy (`--force`, which Archiwista does not offer).
- The jobs' results keep every task and every file (`tasks[]`, `files[]`), so a large project makes a large job result.
- The stand-in producer of the tests has no project operations; the interface of A13 is tested over a Kartograf project of `kartograf.testing`.

**Erratum 1 (2026-10-26, ADR 0032 decision 14):** a job runs the tasks of one manifest of the project: the one of the `producer` the request names (`ProjectJobRequest.producer`, `--producer` of the four commands), else the project's only one. Before a job exists a project of several manifests refuses a request that names none (`400`, `producer_required`) and a producer without a manifest in it (`400`, `other_producer`). The job's `params` keep `producer` when the request named it, so the worker and a retry act on the same manifest; its store and directory checks (decision 5) are that manifest's.
