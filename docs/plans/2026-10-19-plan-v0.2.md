# v0.2 "Previews" implementation plan

**Status:** executed plan of release 0.2.0 (2026-10-20); steps 0–18
completed, acceptance and measurements in `docs/reports/v0.2-measurements.md`.
The criterion of ≥ 30 frames/s with a GPU remains unverified (no access
to hardware WebGL on the reference computer). The spec and plan of v0.3
are written before its implementation. The v0.1 template and contracts:
`docs/plans/2026-10-18-plan-v0.1.md`; the release code: `docs/ARCHITECTURE.md`. After each
step "State after step N" was recorded (commit, deviations and test results).
**Scope (SPEC 13 v0.2):** previews (SPEC 5.7) with a cache keyed by `sha256`;
the "Wachlarz" (the Fan) and the "Oś czasu" (the Timeline) for local data (years and campaigns in the store);
metadata comparison and the curtain (SPEC 8.5, levels 1 and 2); project
own data and snapshots (SPEC 4.7.1, A-ADR-027). The producers' store remains
read-only. Archiwista writes locally the index, the preview cache
and the logs, and outside its data directory only snapshots
in `<data folder>/.wersje/`, on command of a person with the `project.write` permission.
The following apply in order: `PRD.md` (F5, F15, F16, N2, N3, N8.3) and `SCOPE.md`
(stage 3) for matters of scope, `SPEC.md` (especially 4.3–4.7.1, 5.4–5.7, 6,
8.5, 9–11, 13 v0.2 and 14), `DEVELOPMENT_STANDARDS.md` and A-ADR-007, 008,
010, 016, 017, 018, 022, 027, 028 and 029 (with errata). The mockup (`mockup/`;
screenshots `05a`–`05c`, `08`, `17`, `21`–`25`, `27`–`35`) is the starting point
for the layout of the Fan, the Timeline, the "Szczegóły zestawu" (Set details) panel and own data,
and **not** a source of data or logic; the difference of objects between
snapshots shown in it (green "added", red "removed", screenshots `31`–`34`) is
outside v0.2 (SCOPE: "later, by a separate decision"). Each step ends with the given
acceptance test; do not implement the next dependent step until the previous one
works.

## Execution decisions and boundaries

1. **Reference computer and GPU (SPEC 4.5, 13 v0.2).** The same as in v0.1
   (decision 1 of the v0.1 plan: i5-6400, 4 CPUs, 15.6 GiB RAM, SSD `/dev/sdb`
   with ext4; SMB 3 share `<scratch-dir>`). Graphics card:
   NVIDIA GeForce GTX 1060 6 GB (`lspci`: GP106), kernel driver `nouveau`,
   Mesa with `nouveau_dri.so`; nodes `/dev/dri/card0` (`root:video`)
   and `/dev/dri/renderD128` (`root:render`, `0660`). The account the v0.1
   measurements ran under belongs to neither the `video` nor the `render` group, so Chromium
   rendered WebGL in software (SwiftShader: 8–9 frames/s with 4532 footprints,
   19.8 without footprints) — this is a lack of GPU access, not a property of the computer.
   The criterion "≥ 30 frames/s" is measured only with hardware WebGL
   (a WebGL renderer other than SwiftShader, llvmpipe, softpipe), by one of these ways:
   - **(a)** the measuring account in the `render` group (a decision of the
     computer's owner: `sudo usermod -aG render <account>` and logging in again)
     and Chromium from Playwright with GPU flags (`--ignore-gpu-blocklist` —
     `nouveau` is on Chromium's blocklist — and ANGLE on EGL);
   - **(b)** the owner's Chrome started in their graphical session
     with `--remote-debugging-port` and attached to the test through CDP
     (`ARCHIWISTA_BROWSER_CDP=http://127.0.0.1:<port>`).

   Without either of these ways, gate criterion 5 remains *unverified* —
   neither a software measurement nor a lowered threshold replaces it. The proprietary NVIDIA
   driver is an option for the owner, not a requirement of the plan.
2. **Producers: no new requirements (SCOPE: "v0.2 | —").** v0.2 uses
   the public Kartograf 0.8.0 API from the v0.1 plan and the method
   `PinnedTransform.gdal_operation()` (a public class from `kartograf.__all__`;
   the same pinned operation as a PROJ pipeline for GDAL's
   `COORDINATE_OPERATION`, with axis order correction — Kartograf ARCH 1,
   ADR-024). The adapter exposes it in the source contract (step 3), and the contract test
   `tests/contract/test_kartograf.py` checks it. State of Kartograf
   2026-10-19: the branch `feat/archiwista-store-api` is merged into Kartograf's `develop`
   (merge `b71cc370`), and its ref is deleted; the tag `v0.8.0`
   is still missing. The editable install stays, but from Kartograf's `develop` —
   the instruction in the README that points to the deleted branch is fixed by step 18.
   Archiwista takes the georeference of a JPEG with a world file
   from the header footprint KA-4 (decision 5), so it does not pair
   `.jgw` files with versions itself (that is a rule of the `data/` layout, A-ADR-014). Rotation
   in the world file (a non-north-up layout) is a known limitation: should it
   occur in the data, the requirement of an exact raster georeference
   (`raster_georeference(entry)`) goes to SPEC 12 as a proposal after v0.2,
   not as a workaround.
3. **Previews: rendering processes, content-addressed cache, delivery through the
   API.**
   - *Where computed.* The server does not open data files with the GDAL,
     OGR, laspy libraries or `zipfile`. Thumbnails, tiles, vector objects, lists
     of ZIP members, and layer thumbnails and tiles are computed by a pool of long-lived
     rendering processes (`python -P -m archiwista.previews.worker`,
     by default `min(4, cpu)`), killed and started anew after
     a timeout is exceeded (recognition 20 s, tile and layer tile 15 s,
     objects 15 s, ZIP members 10 s, thumbnail 30 s, layer thumbnail
     60 s) or a memory limit (`RLIMIT_AS` 2 GiB, `GDAL_CACHEMAX` 256 MB;
     on Linux — Windows in v1.0). The request queue has ≤ 64 slots (then
     `503 preview_busy` with `Retry-After`), identical requests are computed once
     (one render per key), and a request abandoned by the browser
     (the map was panned) drops out of the queue before rendering. Building
     a local COG (decision 6) is a background job `preview` (A-ADR-007), each
     file in a separate child process with a limit of 10 min and 4 GiB; the job
     builds at most `n = max(1, cpu // 2)` files at a time (2 on the reference
     computer — the targets of decision 12 are counted with this `n`), and at most
     one `preview` job runs (the next ones wait like the v0.1 network jobs).
     The job itself takes one slot of `default_max_jobs()`, and the build processes
     do not take further ones, so that a snapshot and a scan do not wait for
     previews (on 4 CPUs, 2 cores are left for the server, the rendering processes
     and the second job).
   - *Sandbox.* The module `archiwista/sandbox.py` provides the environment for all
     processes that read files (including the v0.1 area reader — one
     implementation instead of code in `areas.py`): minimal variables without
     proxies and credentials, `PROJ_NETWORK=OFF`, `GDAL_HTTP_PROXY` set to a
     closed port, `GDAL_PAM_ENABLED=NO` (without `GDAL_PAM_PROXY_DIR`:
     GDAL statistics write `<file>.aux.xml` next to the data — checked
     2026-10-19 on rasterio's `statistics()` — which in a store breaks "read-only",
     and in the data folder creates a new file for the next scan),
     `GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR` (GDAL does not see neighbouring files:
     `.ovr`, `.msk`, `.aux.xml`, world files), `umask 077` and `GDAL_SKIP`
     for drivers that refer to other files or the network (`VRT`,
     `OGR_VRT`, `GTI`, `WMS`, `WMTS`, `WCS`, `WFS`, `OAPIF`, `OGCAPI`,
     `STACIT`, `STACTA`, `PDS`, `PDS4`, `ISIS3`, `ERS`, `ENVI`, `EHdr`,
     `GML`; the list is in `sandbox.py` and in the test). `GDAL_SKIP` is only a second
     line of defence: the first `WarpedVRT` in a process (rio-tiler) registers
     the VRT driver again, and then a file with VRT content reads the
     `<SourceFilename>` of any server file — also as an overlay
     `a.tif.ovr` with `rasterio.open("a.tif", driver="GTiff")` (checked
     2026-10-19 in `.venv`: rasterio 1.5.2, GDAL 3.12). Therefore: (a) the main
     file is always opened with an explicit driver from the format table
     (`archiwista/formats.py`; extensions from decision 5): rasters
     `rasterio.open(path, driver=…)` (`GTiff`, `AAIGrid`, `XYZ`, `JPEG`,
     `PNG`), and rio-tiler gets an open dataset (`Reader(path,
     dataset=src)`), never the path alone; vectors with a driver prefix
     where GDAL has one (`GPKG:`, `GeoJSON:`), and Shapefile and FlatGeobuf
     (no prefix in GDAL 3.12 — checked) after checking the file
     signature (`.shp`: code 9994, `.fgb`: `fgb\x03fgb`); MapInfo `.tab` only
     as a native table — a view and a joined table (`\IsSeamless`) refer
     to other files, so → `unsupported_format`; (b) `EMPTY_DIR` closes
     overlays and masks from neighbouring files (checked: after `WarpedVRT`
     `a.tif.ovr` is not read, and a Shapefile still reads `.dbf`
     and `.prj`). Consequence: the georeference of a raster comes only from the file itself
     (GeoTIFF, ASC header with `EntryMeta.horizontal_crs`, JPEG from the header
     footprint — decision 2); an own-data raster with only a world file
     → `no_georeference` with a recommendation to save it as GeoTIFF. A user's
     file cannot point to another server file or to an address.
   - *Preview cache.* `<data-dir>/previews/` (permissions `0700`, never
     on a share or in a store): content-addressed objects
     (`objects/<klucz[:2]>/<key>/<renderer>-r<version>/`: `info.json`,
     `cog.tif`, thumbnails, tiles; the version is separate for each renderer —
     `raster`, `vector`, `points`, `archive`, `document`, `composite` —
     so a fix to the vector renderer does not invalidate raster COGs)
     and LRU accounting in `previews/cache.sqlite` (a cache:
     deleting the directory gives an empty cache). The limit comes from the setting
     `preview_cache_limit_gb` (default 20, SPEC 5.7); after a write over the
     limit, the least recently used objects are removed down to 90% of the limit, except
     objects under construction (mechanics: contract "Pamięć"). The key: content, renderer
     version, style and parameters (size, frame, `rescale`). The content is the
     `sha256` of the store version; a version without `sha256` in the sidecar (older
     sidecars, a version without a sidecar) has the key `sha256("path:" + store +
     ":" + version path + ":" + size + ":" + modification time)` —
     versions are immutable, so the key is correct, only without
     sharing with copies of those bytes (A-ADR-008 erratum 3); own
     data — the content identity from decision 8 (the logical SQLite hash without
     R*Tree: a file with the same logical content and a different or damaged
     spatial index gets the same previews — file consistency is
     the folder owner's business, A-ADR-029 point 1). Composite objects
     (layer thumbnail and tile) have the key `sha256("composite:" +
     operation + sorted contents of the ready versions + frame or tile +
     style + size)`. Store versions are immutable, and every change to the
     renderer code raises its version, so the cache is never
     stale; the same bytes in two versions, two stores, or
     in a snapshot and a working file are counted once. A recognition that ended
     in error: `unreadable` goes into `info.json` as the code alone (the library
     message goes only to the request that triggered it, without paths —
     below); `timeout` and `memory_limit` depend on load, so they do not
     go into the cache — the server remembers them for 10 min in process memory,
     so that a repeated request does not kill the rendering process anew.
   - *Permissions before the cache.* Each request first resolves the object
     (`ref`, decision 10) and access to it: the central store is seen by
     everyone, own data and snapshots — only through a project visible to the
     principal (`visible_projects`; invisible → `404 not_found`). Only
     then does it reach into the cache. The cache shares the bytes of equal content
     between projects, but reveals nothing: to hit an object, one must
     already point to a visible file with the same content. Cache objects
     carry no names or paths (`PreviewProbe` without file names, `unreadable`
     as the code alone), error messages leave the rendering process without
     paths (`worker.py` replaces source paths and their directories with the file
     name — otherwise a GDAL message with `/home/ola/projekty/…` would reach
     a person from another project with the same bytes), and `/health` gives
     only numbers. Jobs with project data are visible only through a visible
     project (contract "Zadania"). This is how the plan implements "preview cache keys
     of own data dependent on visibility" (v0.1 plan, step 8b)
     and A-ADR-029 point 3.
   - *Delivery.* Images and tiles go through `/api/v1/…` from the same
     origin, with the session and the `X-Archiwista-CSRF` header like every
     API request (SPEC 10.1): MapLibre adds the header in `transformRequest`
     (it fetches raster tiles through `fetch`, so `connect-src
     'self'` suffices), and `<img>` and the SVG of the Fan get a `blob:` address from the
     `fetch` response (`img-src blob:` is already there). The CSP does not change; no
     signed addresses or tokens in the URL. Headers: store versions —
     `Cache-Control: private, max-age=86400, immutable` (content addressed
     by hash, the store is seen by everyone); own data and snapshots — `Cache-Control:
     private, no-cache` with `ETag`, so every reuse in the browser
     goes through a visibility check (`304` after the check).
4. **Conversions for display only and only with the pinned operation
   (KA-6).**
   - *Footprints as polygons.* In 0.1.0 the WGS84 footprint is an envelope
     (`_polygon(found.wgs84)` in the Kartograf adapter). A sheet rectangle
     in PL-1992 or S-JTSK is a rotated quadrilateral in WGS84 (meridian
     convergence), so the envelope's corner lies far from the sheet's corner
     — measured during planning (2026-10-19, `pinned_transform` to
     EPSG:4326): an SM5 sheet of 2.5 × 2 km at Český Těšín up to 204 m,
     a 5 × 5 km PL-1992 sheet in western Poland 302 m, in the middle of the country
     5 m. At the edges that is more than the error of an approximate operation,
     which KA-6 protects against (SPEC 14: about 100 m). From v0.2 the index keeps the
     WGS84 footprint as a polygon: the native rectangle `Footprint.native`
with edges densified to ≤ 5 km, transformed by
     `GeoAdapter.transformer(native_crs, "EPSG:4326")` (a native footprint
     in EPSG:4326 — without transformation). The R*Tree still holds the bounding box (area
     and map filter), and the local coverage (v0.1) is still computed from the native
     footprint. A producer without a `GeoAdapter` keeps its `wgs84`.
   - *Tiles.* rio-tiler reads through `WarpedVRT`, which converts option
     values to upper case (rasterio 1.5.2, `_warp.pyx`:
     `val = str(val).upper()` for `warp_extras`), so it does not carry a
     PROJ pipeline in `COORDINATE_OPERATION`; `rasterio.warp.reproject`
     preserves the case of this option (exception for `RPC_DEM`
     and `COORDINATE_OPERATION`). An EPSG:3857 tile is therefore produced by
     `reproject` from the nearest overview level (`OVERVIEW_LEVEL`) onto
     the tile grid (morecantile) with a forced operation
     `transformer(file CRS, "EPSG:3857").gdal_operation()`, while rio-tiler
     (A-ADR-008) is used for thumbnails in the file CRS (from an open dataset —
     decision 3), for coloring and for PNG encoding (`ImageData`); statistics
     (p2, p98, min, max) are computed by numpy from a decimated read, not by GDAL
     (decision 3: `.aux.xml`). The technical trial of step 1 confirms both
     observations on a control point before the renderer is built. Exception:
     a file in a CRS on the WGS84 ellipsoid without a change of datum
     (EPSG:4326, EPSG:3857 — SoilGrids, HSG) is transformed with a plain
     GDAL conversion, because Kartograf's policy rejects a conversion without
     a declared accuracy (checked 2026-10-19:
     `pinned_transform("EPSG:4326", "EPSG:3857")` →
     `TransformUnavailableError`), and there is nothing to pin here; for 2180,
     2177, 3045 and 5514 → 3857 a pinned operation exists (accuracy 1 m).
   - *Vectors.* Features in view (`features`) are transformed to WGS84 by the pinned
     transformer (pyproj, like the v0.1 areas); the view rectangle is transformed to the file CRS —
     the same operation in reverse, after edge densification. Before
     transformation the geometries are simplified to about 1 pixel at the zoom
     of the request (parameter `zoom`; `shapely.simplify(tolerance = pixel
     size / 2, preserve_topology=False)` in the units of the file CRS) —
     resampling for display only (SPEC 5.7) — and the response has
     at most 5000 features and 500,000 vertices in total (more →
     `truncated: true` and "Przybliż albo otwórz w QGIS"); without this,
     a BDOT10k or PRG GeoPackage at a low zoom is hundreds of MB, contrary to
     A-ADR-018 ("lightweight previews").
   - *Layer thumbnails* (the Fan): the rendering process composes them in the
     planar CRS of the area (PL → EPSG:2180, CZ → EPSG:5514, like the local coverage)
     with a forced operation. *Layer tiles* (year preview on the map, decision
     7) are composed by the same process: an EPSG:3857 tile of a layer is an overlay (alpha,
     from the oldest to the newest) of the tiles of the versions that intersect it —
     from the cache by version content (A-ADR-008 erratum 2), and missing ones are computed
     by the same code as a version tile.
   - *Control point at the PL/CZ border* (criterion 2): trigonometric point
     3722, k.ú. Mosty u Českého Těšína (ČÚZK, service `BodovaPole`,
     layer 2 "Bod ZPBP určený v ETRS89"): S-JTSK Y = 449,334.63 m,
     X = 1,111,919.25 m (EPSG:5514: x = −449,334.63, y = −1,111,919.25),
     ETRS89 φ = 49.7587324167°, λ = 18.58895625° (GNSS, static method).
     The values from the 2026-10-16 recording in Kartograf's fixtures
     (`tests/fixtures/cz/survey_control/real_2026_10_16/layer_2_tesin_r1000_o0.json`)
     are copied into Archiwista's fixture together with the source (service address,
     object number, recording date). The deviation is computed by `pyproj.Geod`; WGS84
     is treated as ETRS89 (a difference of about 0.9 m in 2026 fits within 2 m
     and is given in the report). The reference values must not be computed with
     the transformation under test. Check during planning (2026-10-19):
     `pinned_transform("EPSG:5514", "EPSG:4326")` places the point 0.67 m from
     the ČÚZK ETRS89 coordinates — there is a margin against the 2 m threshold, so the risk
     lies in the data path (bounding boxes, tiles without a forced operation), not
     in the operation itself.

For each family: file > 2 GB, and for a raster also > 1 Gpx or > 8 GiB
   after decompression → state `needs_build` with no automatic build ("Zbuduj
   podgląd" (Build preview), SPEC 5.7; decision 6); version "brak pliku" → `missing_file`;
   version without `sha256` — preview under the path key (decision 3); store
   disconnected → preview from the cache, and without it `store_unavailable`; CRS
   without a pinned operation → `transform_unavailable` (thumbnail without a map);
   own-data raster with only a world file → `no_georeference`
   (decision 3); read error → `unreadable` (with the library message without
   paths); time exceeded → `timeout`; memory limit → `memory_limit`.
6. **Local COG and large files.** A COG in the preview cache is created for ASC,
   XYZ, JPEG with georeferencing from the footprint, striped GeoTIFF or one without
   overlays with a side > 4096 px, and for the 2D image of LAZ: longest side ≤ 8192 px
   (A-ADR-018: lightweight preview), averaging for continuous values,
   `nearest` for classes, internal overlays, DEFLATE compression (continuous
   values with a predictor) or JPEG (RGB), decimated reading. A file
   ≤ 2 GB — and a raster only ≤ 1 Gpx and ≤ 8 GiB after decompression (width ×
   height × bands × bytes of the type; a few MB of DEFLATE can declare
   100,000 × 100,000 px) — is submitted for building by the interface itself at the first
   preview; a larger one waits for "Zbuduj podgląd" (Build preview) (`POST …/preview`
   with `force: true`). The build is idempotent: a request for
   content already being built joins the running job (`202` with that
   job), for content already built — it answers `200` with the preview description. A COG is never
   a data product: it lives only in the preview cache and has no "to copy"
   path.
7. **Year and campaign layers from local data (the Fan, the Timeline,
   the map).** Layer = variant × data year (`data_year`, never the year of
   download); a version without a year goes to the layer of its release or
   label. The variant has no file format (A-ADR-017, SPEC 6.4): the key
   (`product`, `horizontal_crs`, `resolution`, `vertical_crs`) from the
   `EntryMeta` fields in the index, so segments of one set in two
   formats (e.g. `nmt/pl_1992_1m_evrf2007` with ASC
   and `nmt/pl_1992_ascii-nmt_1m_evrf2007`) give one layer with the formats
   as badges (`formats`), and not two Timeline rows, two Fan
   thumbnails and double counters; when any of the fields is missing,
   the key is the segment (Archiwista does not parse segment names). The parameter
   `group=campaign` splits the year into campaigns (`campaign`). A layer carries
   the area's slot versions (≤ 500, after refreshing the view like
   `/local-coverage`), the local state ("lokalnie 83% obszaru", in the flat
   CRS), footprints in the area's flat CRS (for SVG) and a thumbnail
   composed of sheet previews (A-ADR-008 erratum 2: one tile per version,
   cache by `sha256`; missing ones remain footprints, and their build goes
   as a single `preview` job per layer with progress). Without an area the Timeline
   shows version counts per year and variant. On the map the year preview is
   a single raster source of the layer: `GET /local-layers/tiles/{z}/{x}/{y}.png`
   composes a tile from the version tiles in the rendering process (decision 4), so
   panning the map is one request per view tile — a separate source per
   version would give, with 200 sheets, 200–800 requests per pan against a
   queue of 64 places (`503` without retry in MapLibre) and 6 browser
   connections per origin. The layer source has a `minzoom` from which a
   typical sheet of the layer is ≥ 32 px (a tile then covers at most about
   9 × 9 sheets); below it — footprints only and "Przybliż, aby zobaczyć
   podgląd". Coverage labels on the source, "pobrane" (downloaded) badges, years
   not downloaded from the GUGiK archival WMS and counties from PRG (PRD, "Widoki według
   rodzaju danych") arrive with availability in v0.3.
8. **Own data: folder, reading, content identity, changes.**
   - *Folder.* By default `<project directory>/dane/` (project directory =
     manifest directory after `realpath`, the same key as `project_acl` of the
     state database); Archiwista does not create it — a missing folder is the state "brak folderu
     danych" with a hint. Another folder is set by the administrator
     (`settings.write`; `PUT /projects/{project}/data-dir`) — stored in TOML
     (`AppSettings.own_data_dirs`: project directory → folder), not
     in the producer's manifest. Validation: absolute path, existing
     and readable directory, outside every producer directory of the stores
     (a snapshot must never land in a store), disjoint from the folders of other
     projects (a file belongs to one project, so to one
     visibility) and from Archiwista directories; comparison by `realpath`.
     Administrator only, because the folder is where snapshots are written;
     setting by the project owner — a decision in v0.4 (a departure from
     A-ADR-029 point 2, recorded as its erratum 1). The same rules (without the
     requirement that it exist) apply to the default folder: a project with a manifest
     in a producer directory (SPEC 4.6 point 7: `output_dir` relative to the
     manifest) would have `dane/` inside the store. The scan and the snapshot check the
     folder before each use; a folder outside the rules has the state `invalid`
     with the problem `own_folder_invalid` (reason `inside_store`,
     `inside_app_data` or `overlaps_project`), is not read,
     and the snapshot ends with `snapshot_blocked` with the reason `folder_invalid`.
     A folder containing the folder of another project or lying inside it is
     `invalid` for both projects.
   - *Reading without writing.* The `own_scan` job (from the scheduler every
     `scan_interval_local_min` — all projects; on request from the project view
     or from the CLI — the folder of that project) walks the folder
     skipping hidden directories and files (including `.wersje/` as data)
     and symbolic links leading outside the folder, at most 10,000
     files: from a larger one it indexes the first 10,000 in path order
     (relative path in NFC) and reports the problem `own_folder_too_large`.
     The whole walk of one folder also has shared limits: 50,000 entries
     (including hidden ones and `.wersje/`), 25,000 directories, depth 64
     and 10,000 snapshots. Exceeding any of them reports
     `own_folder_too_large`; the scan aborts the incomplete walk without marking
     files or snapshots not seen in it as missing. The existing
     index stays available until the next full walk.
     A new or changed file (size, modification time, also of the
     `-wal` file) is read by the reader process
     (`python -P -m archiwista.owndata.reader`, sandbox and format table
     from decision 3, 30 s per file, after exceeding it a restart for the following ones):
     GDAL/OGR driver, layers with geometry type, feature count,
     schema, CRS, extent, raster parameters. Shapefile and MapInfo TAB
     (native table only) are sets of files with the same name stem;
     other files — "nierozpoznane" (unrecognised). After every read the folder is byte for byte
     the same: names, sizes and times of data files and `-wal`, no
     new files (an existing `-shm` is the editor's shared memory — SQLite
     may change its content). A SQLite file (GeoPackage) is read according to
     its state (checked 2026-10-19: SQLite 3.46.1, GDAL 3.12): (a) without
     `-wal` — in place, immutable (`immutable=1`, in GDAL
     `IMMUTABLE=YES`) with the file state checked before and after; `mode=ro` is ruled out, because
     for a database in WAL mode (after editing in QGIS) it creates `-wal`
     and `-shm` alongside; (b) `-wal` and `-shm` (file open in an editor) — `sqlite3`
     in `mode=ro` (no new files) and `Connection.backup` (committed
     rows only) to a copy in the process working directory; (c) `-wal`
     without `-shm` (editor crash, copied folder; without `-shm` there is no
     connection that would write) — never in place: `mode=ro` creates
     `-shm` in the folder, `immutable=1` does not see rows from the WAL, and GDAL
     in read mode rewrote the WAL into the main file; a copy of the bytes of the file
     and `-wal` (state before and after, at most 3 attempts) to the process working
     directory and reading of the copy. In states (b) and (c) GDAL reads only the
     copy — likewise the reader, the vector renderer (a consistent copy as
     `source.gpkg` of the object of this content in the preview cache; file > 2 GB →
     `needs_build`) and the snapshot.
   - *Content identity* (`content`: method and `sha256`; snapshot duplicates
     and change detection): `bytes` — SHA-256 of the file; `fileset` — SHA-256
     of the sorted rows `<lower-case member name>\t<sha256>`
     of the set; `sqlite` (GeoPackage and other SQLite databases) — a logical hash
     independent of page layout, WAL and header counters:
     `application_id`, `user_version`, sorted schema entries (without
     internal `sqlite_%` tables, virtual tables and their shadow tables — R*Tree
     is a derived index) and the rows of each table with typed values
     (a table with `INTEGER PRIMARY KEY` in key order, `WITHOUT ROWID` —
     in primary key order, the rest as a sorted multiset of rows).
     Virtual tables and shadows are recognised from `sqlite_master`, not
     from `PRAGMA table_list` (which requires SQLite 3.37, while the index allows
     3.35 — `MIN_SQLITE_VERSION`): a virtual one is an entry with `sql` starting with `CREATE
     VIRTUAL TABLE`, shadows are tables `<virtual>_<suffix>`
     with the suffixes of its module (`rtree`, `geopoly`: `_node`, `_parent`,
     `_rowid`; `fts3`, `fts4`: `_content`, `_segments`, `_segdir`,
     `_docsize`, `_stat`; `fts5`: `_data`, `_idx`, `_content`, `_docsize`,
     `_config`); tables of an unknown module enter the hash (a change of their
     content is a change, never an oversight). Also outside the hash is derived data
     that OGR and QGIS rewrite when opening for writing without
     changing data: the table `gpkg_ogr_contents` (OGR feature counter)
     and the write timestamps `gpkg_contents.last_change` and
     `gpkg_metadata_reference.timestamp`. VACUUM, a WAL checkpoint, a write with no changes
     and opening in QGIS without editing do not change the hash;
     a change of a row, the schema or another `gpkg_contents` column
     does change it.
   - *Changes.* The scan compares the file's content identity with the last snapshot:
     `unsnapshotted`, `unchanged` ("bez zmian od migawki z RRRR.MM.DD"),
     `changed` ("zmieniony od migawki z RRRR.MM.DD" and the hint "Zrób
     migawkę"). The history of observed states (observation time, size,
     modification time, hash, feature count; without content) lives in the index,
     up to 200 states per file. The index is a cache (A-ADR-002):
     a rebuild loses the state history, snapshots stay on disk.
   - *Visibility boundaries.* Own data does not enter `/slots` or
     `/map/footprints` (everyone sees the store, own data — not). It has
     its own resources under `/projects/{project}/…`, so visibility is decided in
     one place — project resolution. On the map it is shown by the project
     context (`project=` in the map address): the layer "Dane własne" (Own data) (file
     extents, features or tiles of the selected one) together with the footprints of the versions
     pinned in the project (a new `project` filter in `/slots`
     and `/map/footprints`; invisible project → `404`).
9. **Snapshots: names, `archiwista-snapshot/1`, procedure, permission.**
   - *Names* (A-ADR-027: "nazwy katalogów i schematu — propozycja do planu
     v0.2"). They stay Polish, like `dane/`, `obszary/` and `zestawy/` in the SPEC:
     these are files for people in the project folder, not code identifiers; ASCII
     characters only. Layout: `<data folder>/.wersje/<file path relative to the
     folder>/<label>/` with a copy of the file (the whole set for
     multi-file formats) and `migawka.json`, e.g.
     `dane/.wersje/sieci/kanalizacja.gpkg/2026-10-18_471d37c0/kanalizacja.gpkg`.
     The full name with extension (the mockup had just the stem `kanalizacja/`)
     separates `kanalizacja.gpkg` and `kanalizacja.shp` from one directory.
     The label `<YYYY-MM-DD>_<sha8>` (date
local creation date, `sha8` = first 8 characters of `content.sha256`), and when
     such a directory already exists (the same content on the same day after a change
     A → B → A) — `<YYYY-MM-DD>_<sha8>_<n>`, n = 2, 3, …, the first free one
     according to the listing of `.wersje/<file>/` right before publication; the order
     of the series follows from `created_at`, not from the names. Working directory:
     `.wersje/.incoming/<host>_<pid>_<token>/` (the same file system as the
     target, SPEC 4.7.1).
   - *Schema `archiwista-snapshot/1`* (JSON in UTF-8, keys in English,
     ISO 8601 dates with offset, sizes in bytes; Pydantic model
     `SnapshotDocument`: write exactly the fields from the table, read
     with `extra="ignore"` — a field added by a newer Archiwista does not make the
     snapshot `invalid_snapshot`, and the full `migawka.json` stays in the index;
     a new optional field — the same `archiwista-snapshot/1`, a new
     required field or a change of a field's meaning — `archiwista-snapshot/2`; a different
     `schema` → problem `unknown_snapshot_schema`):

     | Field | Type | Meaning |
     |---|---|---|
     | `schema` | `"archiwista-snapshot/1"` | format version |
     | `label` | text | label = name of the snapshot directory |
     | `created_at` | date and time | moment of publication |
     | `author` | object | `id` (account or `local`), `kind` (`local_owner`, `user`, `agent`), `name` (display name or `null`), `session` (session label or `null`) |
     | `note` | text ≤ 2000 characters | description by the person |
     | `source` | object | `path` (file relative to the data folder, separator `/`), `format` (GDAL/OGR driver, e.g. `GPKG`, `ESRI Shapefile`, `GTiff`; `null` for unrecognized), `size_bytes` and `modified_at` of the working file at the moment of the copy |
     | `content` | object | `method` (`sqlite`, `fileset`, `bytes`) and `sha256` — content identity (decision 8); the label's `sha8` comes from it |
     | `copy` | object | `method`: `sqlite_backup` or `files` |
     | `files` | list | each file of the snapshot: `name`, `size_bytes`, `sha256` (bytes in the snapshot directory; integrity) |
     | `size_bytes` | number | sum of `files` |
     | `layers` | list or `null` | vector: `name`, `geometry_type`, `feature_count`, `crs`, `fields` (`name`, `type`) |
     | `raster` | object or `null` | `width`, `height`, `bands`, `dtype`, `crs`, `resolution` (`[x, y]`), `nodata` |
     | `feature_count` | number or `null` | sum of features of the layers |
     | `extent` | object or `null` | `crs`, `bbox` (`[min_x, min_y, max_x, max_y]` in the file's CRS), `wgs84` (`[min_lon, min_lat, max_lon, max_lat]` from the pinned operation) |
     | `archiwista` | text | version of Archiwista that made the snapshot |

     Example (abbreviated):

          ```json
     {
       "schema": "archiwista-snapshot/1",
       "label": "2026-10-18_471d37c0",
       "created_at": "2026-10-18T14:02:11+02:00",
       "author": {"id": "local", "kind": "local_owner", "name": null, "session": null},
       "note": "nowy kolektor deszczowy",
       "source": {"path": "kanalizacja.gpkg", "format": "GPKG",
                  "size_bytes": 192512, "modified_at": "2026-10-16T09:41:00+02:00"},
       "content": {"method": "sqlite", "sha256": "471d37c0…"},
       "copy": {"method": "sqlite_backup"},
       "files": [{"name": "kanalizacja.gpkg", "size_bytes": 188416, "sha256": "9c1e…"}],
       "size_bytes": 188416,
       "layers": [{"name": "przewody", "geometry_type": "LineString", "feature_count": 61,
                   "crs": "EPSG:2180", "fields": [{"name": "srednica_mm", "type": "Integer"}]}],
       "raster": null,
       "feature_count": 61,
       "extent": {"crs": "EPSG:2180", "bbox": [566100.0, 241050.0, 569800.0, 246200.0],
                  "wgs84": [19.9201, 50.0402, 19.9719, 50.0866]},
       "archiwista": "0.2.0"
     }
     ```
   - *Procedure* (`make_snapshot` in the worker process of the `snapshot` job):
     (1) plan `check_snapshot` (a twin without writing, DEVELOPMENT_STANDARDS
     1.2): folder valid (decision 8, otherwise `folder_invalid`), file, write
     permission to the folder, free space ≥ 1.1 × size, content identity
     from the last scan against the last snapshot; (2) consistent copy — SQLite
     according to the state from decision 8: (a) `Connection.backup` from an
     `immutable=1` connection and comparison of the file state before and after, (b)
     `Connection.backup` from a `mode=ro` connection, (c) a byte copy of the file
     and `-wal` to the working directory and `Connection.backup` from that copy (this
     is still a SQLite backup, not a byte copy with WAL open —
     SPEC 4.7.1 item 3) — always to a working file in the process's local
     working directory (SQLite does not write on a share), then a byte copy to
     `.incoming`; multi-file formats and the rest — a copy of the whole set with the
     state (size, modification time) of each member before and after, at most
     3 attempts, otherwise error `inconsistent_copy` ("plik zmieniał się
     w trakcie kopiowania — zakończ edycję i spróbuj ponownie");
     (3) content identity of the copy (`sqlite` computed on the copy) and for SQLite
     `PRAGMA integrity_check` = `ok`; the same content as the last snapshot →
     result `unchanged` with its label, working directory removed, nothing new
     in `.wersje/`; (4) `migawka.json`, recomputing the sums of the written
     files, snapshot files read-only (`0444`), `fsync` of the files
     and the directory; (5) label from the listing and publication with a single `os.rename`
     of the working directory to it — an existing target (only a race of two
     processes, e.g. CLI and server or two servers on one share) is an
     error `target_exists`, never an overwrite; (6) snapshot directory `0555` — only
     after `rename`, because moving a directory to another parent requires write
     permission to it (`..` changes; checked 2026-10-19: `EACCES`);
     (7) entry in the index. `chmod` and directory `fsync` rejected by the file
     system (CIFS, ACL: `EPERM`, `EINVAL`) give a warning (`notice`)
     in the job, not an error. Entry (7) is best effort: the source of
     truth is the snapshot directory, and `own_scan` adds missing entries
     from `.wersje/**/migawka.json` (A-ADR-002). An interruption (SIGINT, killed
     process, crash) before (5) leaves at most a directory in `.incoming/`,
     and after (5) — a complete snapshot with read-only files, which the
     nearest scan will find. The scan does not read `.incoming/` as a snapshot,
     and a leftover older than 24 h is reported as problem
     `stale_snapshot_incoming` in the "Dane własne" (Own data) group of the project (SPEC 4.7.1
     says "Magazyn" (Store), but own data belong to the project — SPEC correction
     in step 18). Archiwista does not delete or overwrite snapshots or
     leftovers.
   - *Permission.* New action `project.write` in `Authorizer`: the project
     owner or `admin` (A-ADR-029 item 2: "project changes — owner
     and administrator"); in v0.2 it is required by `POST …/snapshots`, from v0.3 also
     by manifest changes. The agent acts with the rights of the person who issued the token.
     Project not visible → `404`, visible without `project.write` →
     `403 permission_denied`, without the CSRF header → `403 csrf_rejected`. The
     state database needs no migration.
   - *Job `snapshot`:* one at a time per file (`409 conflict` with `job`), no
     network, no write to the store index; the server has no write path to
     the data folder.
10. **`ref` references and comparison (SPEC 8.5, levels 1 and 2).**
    - Every object that can be previewed and compared has a `ref` field
      in the API models: `version:<store>:<version path>`,
      `file:<project>:<path in the data folder>`,
      `snapshot:<project>:<label>:<path in the data folder>`.
      Store identifiers (`[a-z0-9][a-z0-9_-]{0,31}`), project keys
      (`[a-z0-9-]+`) and snapshot labels do not contain `:`, so the
      rest after the second (for a snapshot — third) colon is a path without
      restrictions. The agent copies `ref` from the response, does not build it. The
      HTTP preview routes remain resource-based (SPEC 9.2); an own-data file
      in the address is `file_id` (16 characters of the SHA-256 of the relative path in NFC) —
      one segment, because an arbitrary user path (e.g. with the subdirectory
      `snapshots/`) would confuse the routes.
    - `GET /compare?a=<ref>&b=<ref>` (SPEC 9.2) — level 1: rows
      with a human-readable field name and values A and B, with the difference marked. For
      store versions: normalized index fields (data date and download date,
      label, campaign, submission number, release, full sheet
      and coverage, resolution, CRSs, `nodata`, `sha256`, size,
      license and attribution), then the remaining fields of the raw sidecar as
      flattened JSON paths without interpretation (like the "raw sidecar" of
      v0.1; Archiwista does not know the producer's fields — A-ADR-014). For own
      data and snapshots: feature count per layer, extent, schema
      (fields added, removed, with a changed type), CRS, size,
      content identity, author, note, dates. Mixed pairs are allowed (a snapshot
      with the working file, a version with a version of another slot). Two years (sets of
      versions) are compared visually (the curtain, switching in the Fan)
      with layer summaries side by side — without `/compare` rows. CSV export
      is done by the interface from the JSON response (the server writes nothing).
      Level 3 (difference model, KG) — v1.3; a feature difference of snapshots — a separate
      decision.
    - Level 2: the "Porównanie" (Comparison) view with the curtain (default), blending
      and two synchronized side-by-side views — two MapLibre maps
      with the same position, the curtain through `clip-path` set from JS
      (CSSOM, compatible with `style-src 'self'`). Comparison sides: versions, working
      file, snapshots or two year layers.

13. **Security of the new paths (SPEC 10.1, 10.3).** The client never
    supplies a file path: a version is designated by the index (`resolve_indexed_path`
    in the store root), an own file by a `file_id` from the index in the data
    folder, a snapshot by a label from the index in `.wersje/`; every open goes
    through `realpath` in the root, an outward-pointing link → `403 path_outside_root`.
    GDAL, OGR and laspy work only in sandboxed processes, and open the main
    file with an explicit driver (decision 3); a ZIP is only listed
    (first the end-of-central-directory record, also zip64: > 100,000
    entries or a directory > 64 MiB → `too_large` without `ZipFile`; then
    ≤ 10,000 members, without extraction). Tile and thumbnail parameters are
    validated (0 ≤ z ≤ 22 and 0 ≤ x, y < 2^z, otherwise `422`; a tile with a zoom
    above the file's `maxzoom` or outside its extent → `404 not_found`,
    which MapLibre does not request thanks to the source's `maxzoom` and `bounds`; a layer
    tile below its `minzoom` → `404`; `size` ∈ {128, 256, 512, 1024},
    `style` from the kind's list, `rescale` — two numbers, crop — four numbers
    in a known coordinate system, object `zoom` 0–22). Request body limit unchanged
    (1 MiB; snapshot `note` ≤ 2000 characters). The preview cache and the
    working directories of the processes (SQLite copies) lie in the data directory `0700`. Snapshots
    are written solely by the worker process of the `snapshot` job after checking
    `project.write`; jobs with project data are visible only through a visible
    project (the "Zadania" (Jobs) contract).

## Risks and blockers

- **GPU access.** Criterion 5 requires hardware WebGL (decision 1);
  the measurement account currently has no access to `/dev/dri/renderD128`. Without a decision
  from the computer's owner (the `render` group or measuring through CDP in their
  session) the criterion stays open — a software result does not replace it.
  Chromium may reject `nouveau` despite the flags; then route (b) or the NVIDIA
  driver (owner's decision). If the GPU does not deliver 30 frames/s,
  first measure the components in step 16.
- **Forced operation in tiles.** rio-tiler will not carry over
  `COORDINATE_OPERATION` through `WarpedVRT` (decision 4), so reprojected
  tiles are read by our own code on `rasterio.warp.reproject`. The risk is
  slower tiles for files without overviews — hence COG with overviews
  (decision 6) and measurements in step 16; the trial in step 1 settles it before
  the renderer exists.
- **Consistent SQLite read.** `mode=ro` creates `-wal` and `-shm` next to a database
  in WAL mode without `-wal` and `-shm`, and for `-wal` without `-shm`, `immutable=1`
  loses rows from the WAL, and GDAL in read mode rewrote the WAL into the main
  file (verified 2026-10-19); on top of that come SQLite locks on an SMB share
  and differences in QGIS behaviour. Mitigations: a matrix of three states
  (decision 8) in one place (`consistent_sqlite_read`), GDAL never
  in place when a `-wal` file exists, backup to a local file, state
  before and after, `PRAGMA integrity_check`, trial in step 1. QGIS is not
  installed on the reference computer: the test reproduces a QGIS write (WAL,
  open transaction, crash without `-shm`); a manual trial in QGIS — recommended
  at acceptance on the user's side.
- **Cost of the logical hash.** Reading all rows of a large
  GeoPackage on every change (scan, snapshot). Mitigations: only changed
  files (file state and `-wal`), the snapshot hash computed on its copy,
  measurement in step 16 (target: 100 MB snapshot ≤ 15 s).
- **Leak through new surfaces.** Own data in previews,
  comparison, layers, jobs (`snapshot` with a description, `preview`
  with `file:`), library messages containing paths, the `project` filter and the CLI.
  Mitigations: one `ref` → file crossing point (`ObjectResolver`),
  queries with a required `visible`, job routes with visibility (contract
  "Zadania"), own data outside `/slots` and `/map/footprints`, preview cache
  without names and paths (messages without paths, `unreadable`
  in the cache as the code alone), the visibility matrix extended with every new
  route and with the job routes (step 9).
- **GDAL on untrusted input.** User files can hang or crash native libraries,
  refer to other files (VRT, a `.ovr` overview with VRT content, a linked MapInfo table),
  write next to themselves (`.aux.xml`) and be small on disk but huge after decompression.
  `GDAL_SKIP` alone is not enough — `WarpedVRT` restores the VRT driver (verified).
  Mitigations: an explicit driver for the main file and
  `GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR` (decision 3), `GDAL_PAM_ENABLED=NO`,
  `GDAL_SKIP` as a second line, sandboxed processes, time and memory
  limits, pixel and ZIP entry thresholds before reading, no network, tests
  with corrupted and substituted files; the server does not open data files.
- **Native dependencies.** rio-tiler (numexpr, color-operations) and lazrs
  (Rust) are binary wheels; a lock with checksums, `pip-audit` in the gate, licences
  in step 1; Windows — v1.0.
- **Kartograf without the `v0.8.0` tag.** The read API is on Kartograf's `develop`
  (branch `feat/archiwista-store-api` merged and deleted);
  editable install from `develop`, a contract test (also
  `gdal_operation`) on every Kartograf change. Kartograf is developed by
  a separate team — Archiwista does not change its code.
- **Index rebuild after an update.** The new schema version (steps 3
  and 7b) means a full scan on first start (SSD approx. 50 s, SMB approx. 4 min;
  v0.1 measurements); the state database is unchanged. Described in CHANGELOG and README.
- **Preview cache size and build time.** The Fan of many years
  with ASC sheets means hundreds of COG builds. Mitigations: a 20 GB limit with LRU, COG
  ≤ 8192 px, one build job per layer (≤ 500 versions) with progress,
  `n = max(1, cpu // 2)` build processes and one `preview` job at a time
  (decision 3), builds only for layers being viewed, files > 2 GB and rasters
  above the pixel thresholds only on demand.
- **JPEG georeferencing from the footprint.** Works for world files without rotation
  (CZ orthophoto); rotation or a footprint from outside the header → a thumbnail without a map
  (`no_georeference`), and any requirement for exact georeferencing goes
  to SPEC 12 after v0.2 (decision 2).
- **Scope pressure from the mockup.** The snapshot object difference, years not downloaded
  from WMS, "downloaded" badges, the assistant and the mosaic are in the mockup, but outside
  v0.2 (decision 14); each of these requires a separate decision
  from the user.
- **Growth of snapshots in the project directory (PRD).** The size is in the snapshot
  plan, snapshot usage in the project view; deletion only manually
  outside Archiwista.
- **Deviations from A-ADR-029 until v0.4.** A data folder other than the default is
  set only by the administrator (A-ADR-029 erratum 1); setting it by the project
  owner returns in v0.4 together with the sharing screen. A folder scan
  from the project view is ordered by anyone who sees the project — only that project's
  folder and read-only; a pass through the folders of all projects
  (on an SMB share up to several dozen folders at ≤ 10 s each) is ordered only by the
  scheduler. To be reassessed in v0.4 together with login and request
  limits.
- **Measurement environments.** The SMB share, live-test stores and the GPU
  require explicit `<data-dir>` values and the owner's decision; a missing
  environment means an unclosed criterion, not automatic success.
